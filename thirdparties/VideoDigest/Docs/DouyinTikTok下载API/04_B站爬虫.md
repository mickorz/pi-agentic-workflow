## 2. B站接口特点（与抖音/TikTok 的差异）

1. **不需要复杂签名即可取详情**：`fetch_one_video` 只要普通 GET `api.bilibili.com/x/web-interface/view?bvid=xxx` 加浏览器 UA；
2. **Wbi 签名只保护部分接口**：playurl、用户相关接口需要 wbi 签名；
3. **视频与音频是分离的 DASH 流**：playurl 返回独立视频流（m4s）与音频流，必须 FFmpeg 合并；
4. **风控宽松**：无需登录 Cookie 可取 720P 及以下、公开视频详情、评论。

## 3. Wbi 签名（wrid.py）

`fetch_video_playurl` 等接口的参数要带 `w_rid` 与 `wts`。wrid.py 是一份纯函数实现：

1. 用固定混淆表对 `img_key + sub_key + 参数按 key 排序拼接` 做字符置换，得到 mixin key；
2. 参数串尾接 mixin key 后做 MD5 变换（文件内是手写的 MD5 轮函数，非标准库），输出即 `w_rid`；
3. `wts` 为当前秒级时间戳。

img_key/sub_key 来自 nav 接口（`api.bilibili.com/x/web-interface/nav`，未登录也有返回），有缓存周期。

移植结论：wrid.py 是无依赖纯算法，要么逐函数直译 TS（约 100 行），要么用 npm 现成的 wbi-sign 实现。B站抓取建议直接引用社区成熟的 wbi 方案并配 nav key 缓存。

## 4. 请求构造示例（fetch_one_video）

```text
GET https://api.bilibili.com/x/web-interface/view?bvid={bv_id}
Headers:
  User-Agent: Mozilla/5.0 ... Chrome/130...
  Referer: https://www.bilibili.com/
```

fetch_video_playurl：

```text
GET https://api.bilibili.com/x/player/playurl?bvid={bv}&cid={cid}&qn={qn}&fnval=16&...wbi 签名参数
```

## 5. 移植到 vcli 的步骤

1. 新建 `src/lib/bilibili.ts`：
   - `fetchOneVideo(bvid)`：普通 GET，无签名，最简单，先移植这个；
   - `getBvId(url)`：vcli 的 detectPlatform + b23.tv 短链解析（hybrid_crawler.get_bilibili_bv_id 的逻辑：HEAD 重定向 + 正则 `BV[A-Za-z0-9]+`）；
   - `fetchPlayUrl(bvid, cid, qn)`：需要 wbi 签名时引入 npm wbi 实现；
2. 响应字段：
   ```text
   $.data.title / $.data.desc              标题与简介
   $.data.owner.name                       UP主
   $.data.stat                             播放/点赞/弹幕数
   $.data.cid                              用于 playurl
   $.data.pages                            分P
   playurl: $.data.dash.video[0].baseUrl   视频流
   playurl: $.data.dash.audio[0].baseUrl   音频流（需与视频合并）
   ```
3. 与 vcli 现有链路的关系：
   - 只需要音频转字幕时：playurl 的音频流（dash.audio）直接就是 m4a，比 yt-dlp 下载整条再转码更省流量；但 yt-dlp 已稳定，建议仅在 yt-dlp 失效时启用此路径；
   - 元数据增强（互动数、分P、UP主）可填充 digest 输出的 metadata 字段。
