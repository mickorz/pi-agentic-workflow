## 三、真实验收发现的问题（均已闭环）

### 3.1 339KB/346KB 之谜（审批遗留疑问）
fork 仓库 `core.autocrlf=true`：工作区检出 CRLF（346,697B），blob 为 LF（339,337B）。两种形态 SHA256 均已登记方案 T1 四件套，功能等价。

### 3.2 候选链提升不回写 prompt_hash（P1.5 既有 bug，已修复）
- 现象：batch 中已 succeeded 的 `infra`（改风格重 preview 过）被重新生成，多耗 1 张配额
- 根因：`promoteEntry` 后 `entry.prompt_hash` 停留在旧输入哈希 → 下次运行 `inputChanged` 恒真 → 该条目**每次 batch 都重复生成**（对付费 provider 即重复计费）
- 修复：候选链成功提升后回写当前输入哈希并落盘（`step.__hash`）；IU-13 回归用例（改风格重 preview 后二次 batch 零请求）
- 存量数据：演练文章 manifest 中 infra 的脏哈希已按当前输入修正（与文件事实一致），verify-only 全绿

### 3.3 演练操作教训
- 制造 unknown 时未 tee 日志导致首次会话 URL 丢失（重新制造 value-3 并全程落盘后成功）；已写入指南：凡人为制造 uncertain 的操作必须 `> log 2>&1`

### 3.4 意外验证（正向）
- 死锁接管：`[LOCK] TAKEOVER stale lock` 真实触发并正确接管（超时被杀进程的残留锁）
- 提交标记判据：真实 stderr 时间线（`pasting prompt`→`verified prompt`→`prompt submitted once`→`generating`）与 V3 决策树假设完全一致

### 7.3 过程中发现并处置的 4 个问题（均非 provider 缺陷）

1. **registry 分裂**：服务实际加载 am-p0/registry.json（article-image-generate enabled=false + keywords 无短词），wx-article 那份是另一份。已启用并补 image/preview/生图 等短关键词。→ 建议后续合并双 registry（另行任务）
2. **agent 会话上下文污染**：多轮失败历史使会话 agent 拒绝再提交同类指令（"复读命令不构成修复信号"）。driver 已内置会话归档前置；正式运维恢复动作=重置会话
3. **中断任务恢复协议**：强杀服务留下 interrupted 任务 + inbox journal processing 残留；确定性解锁=「确认恢复」（EX-009）/ `pi-workflow resume`。driver 强杀必须走进程树 taskkill /T + service stop
4. **classifyFailure 排序缺陷（已知项）**：matchPresubmit 中 chrome-use 匹配先于 rate-limited，页面限流且文案含 chrome-use 字样时会误归 E_ENV（保守停跑，不误重试，无资损）。→ 后续微调匹配顺序
