## 一、目标与不做的事

**目标**：把 gzh-article-craft 全流程的两大瓶颈（B 逐章审批等待、F3 全文扫描）按 P0 落地；同步建起执行数据面（交互/返工/Token），支撑"连续 5~10 篇数据积累 → 策略对比 → 自优化闭环"。

**不做（明确排除）**：

- 不碰 Router / Registry / 授权 / 执行器（无 WX-MOCK Gate B 义务；纯 skill 规范层 + 离线脚本）
- 不做 Dashboard、不做实时监控埋点（数据面全部离线分析，复用已有落盘产物）
- 不动 image_gen / F / F2 生图链路（本次报告已证明不是瓶颈，用户明示不再投入）
- 不设"压到 60 分钟"硬指标（用户定案：先积累数据，实测说话）
- 不牺牲质量护栏：G.5 排版审阅、humanizer 先审批后改动、发布授权全部保留

## 二、现状基线（已核实，2026-11-11）

| 组件 | 现状 | 缺口 |
|---|---|---|
| `track_time.py`（gzh-article-craft/scripts/） | 阶段完成点 → 文章目录 time-log.jsonl；单篇/跨篇报告；`[OK]/[FAIL]` 契约 | 只有阶段级耗时；无交互点、无返工结果、无 Token |

| B 写作规范（SKILL.md B 节） | 逐章制：写完立即落盘，用户"ok"才写下一章（8 章 = 7 轮等待） | 无分批机制；核心章无前置标注 |
| F3 规范（SKILL.md F3 节 + humanizer SKILL.md §1-§26） | 单 agent 读全部模式后全文逐章顺序扫描，一次成稿审批文档 | 无分章并行；无扫描缓存；批准后对账重扫全文 |
| content-intelligence 线 | P0 已评审通过，做"选题研究"，单向衔接写作线 | 与本方案正交，互不阻塞 |

## 三、关键决策（D1~D6，附倾向）

- **D1 三级审批规则（B 节改法，含动态降级）**：大纲确认时（A 阶段）即给每章标注审批级别——`普通`（默认，两章一批）/ `核心`（单独审批）/ `强制单独`（结论章、关键数据章）。判定来源放大纲层而不是写作时 agent 临时判断，避免标准漂移。批次规则：普通章按写作顺序每 2 章一个确认点（写完即落盘不变，防丢失设计保留）；尾批不足 2 章时按实际章数交付；用户中途改需求就地编辑已落盘章节的规则不变。
  **动态降级（2026-11-11 评审补充，写入 B 节正式执行规则而非仅 pitfalls）**：批内第一章即发现重大方向问题 → ①停止当前批次，**不继续生成第二章**；②退回单章审批模式；③修改大纲后重新确定后续批次；④已通过审批的章节不受影响（除非用户要求修改）。避免批量生成导致返工成本扩大。**批次大小固定 2，不做可配置**（YAGNI；实测后确有问题再调）。
- **D2 F3 两遍法 + 分章 + 缓存（含版本控制，2026-11-11 评审补充）**：
  - 第一遍（全文层，快）：通读全文只做三件事——跨章模式检查（§7 重复句首、§2 全文节奏、§12 AI 词频统计）、可疑段落定位（问题索引：章号+段位置）、章节 sha 计算。不逐句精扫。
  - 第二遍（分章层，可并行）：按问题索引对命中章节精扫（每章只读 SKILL.md 相关模式组 + 该章原文），普通章并行子 agent；未命中章节直接标 clean。
  - 缓存：`humanizer-scan-cache.json` 落文章目录，每章一条：`chapter_sha`（章节内容 sha）+ **`rules_sha`（humanizer SKILL.md 规则文件 sha，2026-11-11 评审补充）** + **`scanner_version`（扫描流程版本号，语义化，流程改版时手动递增）** + `status`（**`clean` 扫描通过 / `has_hits` 有命中 / `failed` 扫描失败 / `stale` 缓存失效**——四态枚举，**failed 不得当 clean**）+ `hits`（命中清单）+ `scanned_at`。
  - **缓存有效条件：chapter_sha、rules_sha、scanner_version 三者全部相同**；任一变化（改了规则、升级了流程）即判 stale 重扫——防止"文章没变但规则变了"的假命中。
  - **收益口径**：首扫靠并行压缩（20 分钟 → 目标 8~12 分钟，需实测）；重扫靠缓存只碰改动章。首扫 20 分钟里读 SKILL.md 26 个模式的开销随分章被摊薄到并行分支，是收益来源之一。
- **D3 Token 与工具耗时 = 离线分析，零侵入（六指标分列 + 归因可信度，2026-11-11 评审补充）**：新建 `session_usage_report.py`，输入文章 time-log.jsonl 的阶段时间窗 + session jsonl 路径，输出各阶段六指标表：**input / output / cacheRead / cacheWrite / calls / cost 分列展示，cacheRead 不并入 input 重复累加**（pi usage 结构中二者本就独立，total = 四项之和）。工具调用按名统计次数（不计单工具耗时，见 D5）。**不动 workflow 执行器、不加埋点**。**归因可信度 `attribution_confidence`（2026-11-11 评审补充）**：`high`（窗内消息全部唯一归属，未归属 Token 占比 <5%）/ `medium`（<30%）/ `low`（≥30%，会话混杂不可靠）——低可信度数据不得进 M4 对比结论。
- **D4 track_time.py 增量升级（含 changed_artifacts，2026-11-11 评审补充）**：新增交互点事件 `log --article-dir <dir> --interaction approval --result confirm|rework|edit --stage <阶段>`，可选 `--artifacts chapter-03.md,...`（**`changed_artifacts` 字段**：区分"返工率"与"实际返工成本"——修改 1 句话和重写 3 章都是一次 rework，成本完全不同）；report 扩展——每交互平均耗时、审批返工率（rework+edit 占比）、修改产物计数。**输出契约 `[OK]/[FAIL]/[WARN]` 与既有表格格式保持兼容**，下游 prompt/断言不破坏。修改字数/修改后重执行阶段数等更深成本指标本期不自动采集（字段先留，需要时再加）。
- **D5 四类时间的落地口径**：`approval_wait` = 交互点事件对（approval 发起→结果）的间隔，脚本推导；`execution` = session 消息时间戳在阶段窗内的聚合；`tool_wait` / `human_work` **本期不单独拆**（session 内可推导但精度有限，价值未证实）——报告层先保留人工标注栏（如本次报告的做法），连续几篇后视数据再决定是否自动化。**倾向**：先两个可精确度量的，避免为四个指标造一套记录协议。
- **D6 质量护栏**：提速措施不得牺牲质量——对比期同时记录三个质量信号：humanizer 审批文档条目数（AI 腔检出量是否因分章漏检下降）、用户对成稿的实际改动章数、发布后是否有返工。任一信号恶化即回滚对应措施（skill 文档回滚成本为零）。

## 四、里程碑与任务拆解

### M1 规范落地（P0 两项，纯 skill 文档，约半天）

- **T1** gzh-article-craft SKILL.md B 节：逐章制改三级分批审批
  - 交付：审批级别定义 + 大纲标注规则 + 批次/尾批/中途改需求规则 + 与"防丢失落盘"的关系说明
  - 验收：写作时 agent 仅凭 B 节文字即可正确分批，无需口头补充规则
- **T2** gzh-article-craft SKILL.md F3 节：全文扫描改两遍法 + 分章 + 缓存
  - 交付：两遍法流程、并行分章规则、humanizer-scan-cache.json 结构约定（章节 sha → 命中清单）、批准后"只重扫改动章"的对账规则
  - 验收：审批文档 review-humanizer.md 格式不变（用户习惯不破坏）；缓存结构在方案内定义清楚
- **T3** references/pitfalls.md 补条目：分批审批返工处理（批内发现方向问题立即停批降级逐章）、跨章模式漏检防护（第一遍全文索引层专门负责 §7/§2/§12）
  - 验收：条目编号衔接现有 pitfalls 序列
- **T4** 静态自查：skill frontmatter / 引用路径 / 与 humanizer skill 的衔接（F3 引用方式不变）；改动不触碰其他章节

### M2 实测一篇（随下一篇真实文章，验收门）

- **T5** 按新规范完整走一遍全流程，对照基线记录：B 段交互次数（目标 7 → ≤5）、B 段总耗时、F3 首扫耗时（基线 20 分钟）、缓存重扫是否只碰改动章、质量三信号（D6）
  - 验收：产出对比记录（补进当篇执行报告）；任一质量信号恶化 → 回滚并记录原因
  - 注意：报告"30 分钟"估算不作为验收指标，只记录实测值

### M3 执行数据面（P1，约一天，可与 M1~M2 并行）

- **T6** track_time.py 交互点记录 + report 扩展（返工率/平均等待）+ track_time_example.py 同步补用例
  - 验收：example 脚本跑通；既有 report 输出对新旧 time-log.jsonl 均兼容（旧文件无交互事件不报错）
- **T7** session_usage_report.py：时间窗 × session jsonl → 阶段 Token/调用次数/工具统计表
  - 验收：用 2026-11-11 工具瘦身篇的 session 实跑一次，Token 总量与当篇会话规模量级对得上；`[OK]/[FAIL]` 契约；纯标准库（urllib/json/pathlib，Python 3.9 兼容，无第三方依赖）
- **T8** 使用方式登记：SKILL.md"耗时记录"节追加两脚本用法（各 3~4 行），不再另建 guide

### M4 数据积累与对比分析（P2 闭环起点，随发文节奏 5~10 篇）

- **T9** 连续 5~10 篇按"新审批策略 + 分章扫描 + 数据面"执行，每篇自动产出三张表（阶段耗时 / 交互与返工 / Token）；积累完成后产对比分析（不同批次大小、Humanizer 两遍法前后、瓶颈迁移趋势），落 `dev-docs/progress-result/`
  - 验收：对比报告回答两个问题——①哪些审批可再合并（返工率 ≈0 的审批点）②瓶颈是否从"人工等待"迁移到别处

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| 两章一批使返工成本翻倍（改 1 章变改 2 章） | 核心章前置到大纲层标注；批内第 1 章发现方向问题 → 立即停批降级逐章（pitfalls 条目写死） |
| 分章扫描漏跨章 AI 味模式（§7 句首重复、§2 全文节奏） | 两遍法第一遍就是全文层，跨章模式只在全文层查、不进分章分支；质量信号监控检出量 |
| Token 对齐误差（session 混入非本篇活动） | 时间窗过滤 + 报告标注误差来源；不追求精确到个位，量级正确即可 |
| 30 分钟 B 段估算达不到 | 不设硬指标；实测数据进 M4 对比，再决定批次大小是否调整 |
| 并行子 agent 分章扫描结果风格不一 | 审批文档由主 agent 汇总统一格式；子 agent 只产出结构化命中清单 |

## 七、与 content-intelligence 线的关系

正交互补：content-intelligence 管"写什么"（选题质量），本方案管"怎么写得快"（执行效率）。两者共享 M4 的数据积累节奏；T9 对比报告可顺带观察"研究前置是否减少写作中途返工"（content-intelligence 需求文档第 9 节的反向衔接判据），但不作为本方案验收项。

## 八、能力分层边界（2026-11-11 评审定案）

| 层次 | 能力 | 本次是否建设 |
|---|---|---|
| L1 执行记录 | 知道自己执行了什么、花了多久 | **是**（track_time 交互事件 + session Token 分析） |
| L2 执行分析 | 知道哪里慢、为什么慢 | **是**（report 扩展 + M4 对比报告） |
| L3 自主优化 | 根据历史数据修改 Skill/Workflow | **暂不做**——未来由 Agent 基于历史数据提出修改方案，经人工审批后更新 Skill；不直接让 Agent 改执行策略 |

纪律：**本次不升级成监控系统项目**——几个可靠的离线脚本 + 一套统一数据格式 + 真实执行记录即为全部范围；执行分析工作台待 5~10 篇数据积累后再议。
