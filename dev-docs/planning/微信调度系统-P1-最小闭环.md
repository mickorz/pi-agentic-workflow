## 2. 目录与契约（先类型后实现，NFR-002）

```text
src/gateway/
  bot-adapter.ts        # BotAdapter 接口：onMessage/send/start/stop；统一消息格式（WG-001）
  wechat/               # P0 决策对应的实现（Extension 桥接或独立协议适配）
src/dispatch/
  registry.ts           # WorkflowRegistry：注册/校验/检索/启用（WR）
  intent-router.ts      # IntentRouter：意图分类+候选匹配（IR）；LLM 提示与解析可注入
  conversation.ts       # ConversationStore：待补参数/当前任务/TTL（CV）
  dispatcher.ts         # plan()/execute() 两段式（§2.1）：无副作用路由计划 + 显式执行校验链 → RunApplicationService（EX）
  task-store.ts         # TaskBinding 持久化（.pi-wechat/tasks.jsonl）
src/model-routing/
  model-router.ts       # ModelRouter 契约 + 路由决策记录（MR）
  bifrost-adapter.ts    # 或 strategy-port.ts（按 LK-02 决策命名）
src/notify/
  notifier.ts           # NT-001~003 直发实现（P2 换 Outbox 驱动）
src/cli/commands/wechat.ts   # pi-workflow wechat start：装配并长驻
tests/unit/wx-*.test.ts      # 全 Fake 注入单测
dev-examples/wx-p1/          # 手动脚本 + 40 条路由样例
```

**接口签名以《需求》§7 契约为准**：`BotMessageReceipt`、`ConversationState`、`WorkflowRegistration`、`TaskBinding`、`ModelRoutingDecision` 五个持久化实体在 P1 全部落地（Outbox/Audit 留 P2）；存储按 LK-04（`.pi-wechat/` 下 JSONL + 原子写，复用 `run-store.ts` 的原子写工具）。

**ModelRouter 与现有 `agent({model})` 的接法**（MR-012 兼容要求）：

- 优先级实现为决策函数：显式物理模型 > 节点 tier > Workflow 默认策略 > 自动分类/默认 tier（《需求》§8）。
- 接入点在 `PiAgentAdapter` 之前包一层路由解析（或以 `defaultModel` 动态注入等效机制），**不改 DSL 语义**；`nodeId → requestedTier → actualModel → routeSource` 写入运行记录（事件或 result 摘要）。
- Journal 回放一致性（D-04）：路由决策发生在节点执行前，作为身份哈希输入的一部分沿用现有机制；若 P0 结论要求决策冻结进 journal，在 T5 一并落。

### 2.1 共享契约约束（跨入口复用，Router POC 依赖于此）

> 修订依据：冲突分析 V2（eac981d）§四。本节是 P1 的硬性设计约束，不是可选项；违反即 Gate-out 不通过。

**（1）plan() / execute() 分离**（dispatcher.ts 必须提供两个逻辑操作）：

```typescript
// 只分析，不产生 Workflow 副作用：不启动 Run、不写 TaskBinding、不发送任何通知
const plan = await dispatcher.plan({ text, context });

// 显式请求执行：重新校验 Registry 版本、目标脚本、参数、身份、权限与风险策略
// 内部仍是唯一启动入口 RunApplicationService.start()，不得直调 engine
const result = await dispatcher.execute(plan, { actor, authorization, entrypoint });
```

- `plan()` 结果**不是永久授权**：`execute()` 必须重新过全部校验链（两调用间隔内 Registry 可能已变更）。
- Router POC 批量评测只调 `plan()`，零执行副作用。

**（2）Intent / Action 分离**（意图是用户请求类别，动作是系统接下来的事，不得混入同一枚举）：

```text
Intent（五类，沿用 IR-001）：chat | execute_workflow | clarify | task_control | unsupported
Action（独立枚举）：start_execution | ask_clarification | refuse | perform_task_control | chat_reply
示例："帮我翻译一下" → Intent=execute_workflow + Action=ask_clarification（参数不完整）
```

**（3）跨入口复用禁合**：`src/dispatch/`（含 registry/intent-router/dispatcher/conversation）
禁止 import `src/gateway/` 与微信协议实现；必须可被 CLI 直接调用（T1 单测须包含无 Gateway 的直调用例）。

**（4）共享评测契约**：`dev-examples/wx-p1/routing-samples.json` 为唯一样本库，字段含
`scenario`、`channel`（cli/wechat）、`expectedIntent`、`expectedAction`、`expectedWorkflowId`、`expectedArgs`；
评测入口支持 Fake LLM 与真实 LLM 双模式；统计口径区分“模型调用失败”与“合法 unsupported 决策”。
Router POC 复用并扩展此样本库，不另建一套。

**（5）执行前授权与执行中审批的边界**（防“先启动后确认”漏洞）：

- **执行前授权**：`write` / `external-side-effect` 风险等级的 Workflow，其用户确认必须发生在
  `RunApplicationService.start()` **之前**（Dispatcher.execute 校验链的一环）；不允许先启动高风险
  Workflow 再等确认——否则首个节点可能已发生文件写入或外部操作。
- **执行中 Checkpoint**（EX-007/008）：用于 Workflow 运行过程中的阶段审批，**不能代替启动授权**；
  两者是独立门禁，缺一不可。
- 实现锚点：execute() 对 `riskLevel != read-only` 且未携有效授权的请求直接拒绝（NOT_AUTHORIZED），
  而不是降级为“启动后等待审批”。

## 3. 任务拆解（建议顺序）

| 任务 | 内容 | 验收锚点 |

| T3 IntentRouter | LLM 提示词（含候选元数据而非源码，IR-002）+ 结构化解析 + 服务端强校验 | IR-003/004/007 负例 |

## 5. 风险与回滚

- LLM 意图输出不稳定 → 样例集持续扩充 + 置信度门限（LK-05）+ 失败即 unsupported（不默选，IR-004 兜底）。
- 微信通道在开发期失效 → 全链路可用 FakeBot 驱动开发，真机验证集中在 T7/T9。
- ModelRouter 接入点侵入 runtime → 保持包装层方式，不改 `workflow-runtime.ts` 核心路径；若必须改，单独评估对 Journal 哈希的影响并记录迁移说明（NFR-006）。
