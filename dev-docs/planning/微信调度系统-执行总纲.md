## 2. 已锁定的技术决策（继承《需求》§13，执行期间不再重议）

| 编号 | 决策 | 内容 | 依据 |
|---|---|---|---|
| LK-01 | 微信接入 | M0 两条路径都做**薄验证**（Pi Extension 内运行 / 抽取协议模块独立进程），**长期目标为独立 BotAdapter**；P1 按实测结论实施 | 《需求》§13-1 建议 |
| LK-02 | 模型路由 | 以 P0 实测（C-03）为准：Bifrost 扩展若能作用于独立 `createAgentSession()` 则直用；否则抽取其 tier/池/健康策略实现独立 `ModelRouter`。两条路径都要保持 `ModelRouter` 契约稳定 | 《需求》MR-007、§13-2 |
| LK-03 | 风险默认 | V1 **仅 `read-only` Workflow 允许自动执行**；`write` / `external-side-effect` 必须执行前显式确认 | 《需求》§13-3 建议 |
| LK-04 | 持久化 | 本地 JSONL + 原子 manifest（与 `run-store.ts` 同风格），数据目录 `.pi-wechat/`；**不引入数据库** | 《需求》§13-4 建议、NFR-005 |
| LK-05 | 默认配置 | chat 默认关闭（命中 `chat` 意图回固定提示语）；路由置信度门限 0.75；待补参数 TTL 15 分钟；通知重试上限 24h；这些值全部进配置文件可调 | 《需求》§13-5 |
| LK-06 | 代码位置 | 单仓库 monolith：新模块进 `src/`（`src/gateway/`、`src/dispatch/`、`src/model-routing/`、`src/notify/`），入口为 CLI 子命令 `pi-workflow wechat start`；**不新建 npm 包** | NFR-001、§4"不规定进程数" |
| LK-07 | 三方代码 | 仅以 git submodule 引用（已接入 `thirdparties/pi-wechat-assistant`、`thirdparties/pi-bifrost`、`thirdparties/pi`）；可复用模块优先以适配层调用，**fork/vendor 需登记许可证与上游版本** | 《需求》§8 末段、D-08 |

## 4. 贯穿性硬约束（每个 P 文档默认继承，不再重复）

1. **执行唯一入口**：一切 Workflow 启动走 `RunApplicationService.start()/resume()`，禁止另造执行引擎（《需求》EX-001）。
2. **白名单硬边界**：LLM 输出的一切 `workflowId`/路径/参数必须经 Registry + Schema + 权限服务端校验；`confidence` 不是授权（IR-003/007、NFR-004）。
3. **幂等**：`channel+messageId` 去重贯穿全链路；重复审批幂等或拒绝（WG-003、A06/A12）。
4. **可测性**：BotAdapter/IntentRouter/ModelRouter/WorkflowRunner 全部可注入 Fake（NFR-002）；单测不依赖真实微信与真实 LLM。
5. **不回归**：每阶段 Gate-out 必含 108 单元测试 + V1/V2 手动套件回归。
6. **文档同步**：每阶段完成更新 `dev-docs/progress/执行进度.md` + `dev-docs/progress-result/` 阶段报告（沿用现有 P0~P3/V2-P0 报告命名，本项目用 `WX-P0-执行报告.md` 等前缀避免与主项目阶段混淆）。
7. **经验沉淀**：踩坑即写 `dev-docs/experience/`（先查旧经验再动手）。
