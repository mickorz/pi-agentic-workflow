## 1. 总顺序

```text
WX-P0 → WX-P1 → WX-P2 → WX-PT → RP-P0 → RP-P1 → RP-P2 → RP-P3
└────────── wechat-dispatch 主线（V1 交付）──────────┘└── Router 评测工具线 ──┘
```

## 3. 排序依据

1. **WX-P0 必须最先**：LK-01（微信接入路径：Pi Extension vs 独立 BotAdapter）与 LK-02（Bifrost 能否作用于独立 `createAgentSession()`）直接决定 WX-P1 的 T7（微信接入）与 T5（ModelRouter）的实现方式——决策未落定就开 P1 必然返工。
2. **WX-P1 是一切的地基**：Router 工具的本质是「复用」——复用 `src/dispatch/` 的 Registry/IntentRouter/Dispatcher 与 `routing-samples.json` 唯一样本库（PRD V2 §0 修订核心）。共享模块在 WX-P1 落地之前，评测工具无从建起。
3. **Router 排在 WX-PT 之后是 PRD 硬约束**（§0 前置条件原文：「本工具不单独启动开发，排在微信 PT 之后」）；冲突分析 V2 已按此消除两线并行修改同一模块的风险（无第二套 Registry/Router/执行入口）。
4. **RP-P3 收尾闭环**：规模实验产出的检索升级建议，正是微信 P3 扩展预留中 IR-010（BM25/向量检索）的决策输入，形成「做出来 → 验证够不够好 → 指导下一步」的闭环。

## 4. 轨道外事项

| 事项 | 处置 |
|---|---|
| 主项目 **V2-P1/P2/P3**（Web Server / React 工作台 / E2E 交付） | 与微信线无模块冲突，作为第二轨道；建议排在 WX-PT 之后（微信 P3「可视化管理」本就计划与 V2-Web 汇合，先交付微信 V1 再回头做 Web 更顺） |
| 微信 **P3 扩展预留**（附件/多用户/多 IM/热更新/可视化/成本分析） | 文档明确「不排期、不设 Gate」；其中检索升级待 RP-P3 数据，可视化待 V2-Web 汇合 |
| 每阶段通用纪律 | 每任务一 commit；Gate-out 前跑全量回归（108 单测 + V1/V2 手动套件）；完成后更新 `dev-docs/progress/执行进度.md` + `progress-result/` 阶段报告（WX-P<N>-执行报告.md）；踩坑即沉淀 experience |
