## 一、推荐架构：两个独立 Workflow + 一个总 Workflow

微信发送 GitHub URL 后的总体架构：

```
微信发送 GitHub URL
        |
        v
+-----------------------------+
| Workflow A: github-research |
| 读取仓库 -> 分析项目 -> 保存知识库 |
| 可独立执行                    |
+-----------------------------+
        |
        v
+-----------------------------+
| Workflow B: github-article  |
| 读取知识库 -> 套用模板 -> 生成文章 |
| 可独立执行                    |
+-----------------------------+
        |
        v
+-----------------------------+
| 现有公众号流水线（复用，不重做）  |
| 审稿 -> 配图 -> 草稿箱 -> 审批发布 |
+-----------------------------+

总 Workflow: github-recommend
负责串联 A、B，不重复实现业务逻辑
```

## 二、为什么要拆成两个

后续存在三种独立需求场景：

| 微信输入 | 执行流程 |
|---------|---------|
| 「帮我研究这个 GitHub 项目，保存知识库」 | 只执行 A |
| 「把知识库中的 UI-TARS 写成推荐文章」 | 只执行 B |
| 「推荐这个 GitHub 项目，做成公众号文章」 | A → B |

还有一个非常重要的好处：**文章生成失败，不影响已保存的知识库。**

以后想重新生成文章，不需要重新请求 GitHub 和分析项目，可以直接读取已有的研究结果。

## 三、在本仓库的落地方式

Runtime 已支持 `workflow()` 子流程调用（`src/runtime/workflow-runtime.ts` P1 已实现，
含路径解析、自环检查、深度限制、structuredClone 参数隔离），**不需要改造底层引擎**。

建议目录（沿用 `dev-examples/wx-article/` 现有布局）：

```
dev-examples/wx-article/
├── scripts/
│   ├── github_research.js       # GitHub研究（新写）
│   ├── github_article.js        # 推荐文章生成（新写）
│   ├── github_recommend.js      # 总编排（新写）
│   │
│   ├── article_prepare.js       # 已有
│   ├── article_image_generate.js# 已有
│   └── article_publish.js       # 已有
│
└── registry.json                # 登记新 workflow
```

总 Workflow 的核心逻辑（示意）：

```js
// 1. GitHub 项目分析与知识库保存
const research = await workflow(
  "./github_research.js",
  { url: args.url }
);

// 2. 基于研究产物生成文章
const article = await workflow(
  "./github_article.js",
  { projectId: research.projectId }
);

// 3. 返回文章结果，等待后续处理
return {
  projectId: research.projectId,
  articleDir: article.articleDir
};
```

实际实现还需要加入：失败检查、重复项目检测、知识库更新策略、本地写入审批（详见执行方案）。

**关键接口约定：A 和 B 之间只传 `projectId`（或稳定的研究产物引用）**，
避免让文章生成依赖 A 的内部文件组织方式。

## 四、ID 管理原则：项目 ID 与文章 ID 分离

同一个 GitHub 项目以后可能生成多篇不同角度的文章（入门推荐 / 深度评测 / 技术选型……），
所以：

- **知识库项目 ID（projectId）** 与 **公众号文章 ID（articleId）** 必须分开管理；
- 允许一个项目关联多篇文章（一对多）；
- 项目档案中记录文章关联列表，文章侧记录来源 projectId。

## 五、开发计划：一次需求，分两个阶段

| 阶段 | 开发内容 | 验收标准 |
|-----|---------|---------|
| P0 | `github-research`：GitHub 抓取与知识库归档 | 输入 URL，生成可追溯的项目档案 |
| P1 | `github-article`：模板写作 + `github-recommend` 总编排 | 从知识库生成文章，衔接现有草稿流程 |

两个阶段放在一份需求文档和执行方案中，但 **P0 必须能独立验收**，
不能依赖公众号文章生成成功才算完成。

## 六、最终形态

不是两套独立系统，也不是一个几百行的大 Workflow，而是：

```
一个 GitHub Research 能力（A）
+ 一个 Article Generator 能力（B）
+ 一个薄编排层（总编排）
```

工作量相对可控；未来容易扩展为 GitHub 项目对比、技术选型、企业解决方案推荐等 Workflow。

## 七、留给人肉评审确认的决策点

| 决策点 | 建议默认 | 备注 |
|-------|---------|------|
| 知识库数据落点 | vault 级 `70_KnowlegeBase/01_Github/`：config 显式 `github_knowledge_root` 优先，缺省从 article_workspace 向上回退定位 | 知识库是持久资产，不落 dev-examples（dev-examples 可随时删）；路径已适配用户 vault 目录规划（2026-10-26 定版） |

| 重复项目策略 | 默认命中即复用（reused=true 不重抓）；`force=true` 才重新抓取更新 | 更新时保留已有文章关联 |
| 文章生成后是否自动衔接配图/草稿箱 | 不自动，输出交接提示，由用户用现有 `article-prepare` 继续 | 与 idea-article-handoff 同一原则（不自动嵌套、不发布） |
