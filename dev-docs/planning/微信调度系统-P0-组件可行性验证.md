## 1. 目标

回答两个问题并落为决策，供 P1 直接实施：

- **微信怎么接**（LK-01）：Pi Extension 内运行 vs 独立 BotAdapter，实测可行性。
- **模型路由怎么接**（LK-02）：Bifrost 扩展能否作用于本项目 `PiAgentAdapter` 的独立 `createAgentSession()`；不能则确定抽取哪些策略模块。

## 2. 任务拆解

### T1 pi-wechat-assistant 源码结构分析（纯阅读，0 成本）

- 通读 `thirdparties/pi-wechat-assistant/`：`src/wechat/`（iLink 协议）、`src/bridge/`（桥接）、`src/extension/`（Pi Extension 入口）、`docs/architecture.md`。
- 产出清单（进验证报告）：
  - 模块清单：每个模块的职责、对 Pi 运行时（Extension API/上下文）的依赖点、纯 Node 可复用性判定。
  - 登录态/凭据存储位置与格式；长轮询/去重/游标机制；消息发送 API 形态。
  - 明确"若走独立 Adapter，需要抽取/复刻哪几个文件"。

### T2 微信收发薄验证 — 路径 A（Pi Extension 内）

- 按 pi-wechat-assistant 文档安装为 Pi Extension，扫码绑定，手机微信发一条文本 → Bot 回一条固定文本。
- 记录（C-01）：绑定流程、消息往返时延、iLink 授权失效表现、断线后轮询是否自愈。
- 结论项：该路径能否承载"长驻接收 + 主动发送"（不依赖用户先发消息时的主动推送能力边界）。

### T3 微信收发薄验证 — 路径 B（独立进程 BotAdapter）

- 依据 T1 清单，用最小代码（可放 `dev-examples/wx-m0/standalone-adapter.ts`）在本项目普通 Node 进程内复用其协议模块完成同一收发验证。
- 记录：哪些模块直接 import 可用、哪些 Extension API 需要垫片（如 logger/事件总线）、登录态共享冲突（与路径 A 同账号并存时的表现）。
- **决策 LK-01 落地**：路径 B 可行 → P1 以独立 BotAdapter 为准（Extension 路径仅留作对照）；路径 B 不可行 → 记录阻断点，P1 降级为 Extension 桥接模式并明确其生命周期约束（D-02）。

### T4 Bifrost 兼容性验证（C-03）

- 前置阅读：`thirdparties/pi-bifrost/`（README、index.ts、routing.ts、config.ts、docs/guide/routing-controls.md）；Pi SDK 扩展装载机制（`thirdparties/pi/packages/coding-agent/docs/sdk.md`、extensions.md）。
- 实验 1：本项目 `PiAgentAdapter` 的 `createAgentSession()` 场景下，Bifrost 扩展是否被加载（`resourceLoader`/extensions 发现路径）、`bifrost/auto` 是否被解析为物理模型。
- 实验 2：显式 `model` 优先级——节点写死物理模型时 Bifrost 是否静默改写（对照《需求》MR-003/A09 语义）。
- 实验 3：子 Agent 会话（`SessionManager.inMemory` + 多会话）下 Bifrost 状态是否互踩（C-04 隔离，一并覆盖微信 Bot 重复初始化检查点）。
- **决策 LK-02 落地**：可用 → P1 写薄适配直接调；不可用 → 从 bifrost 抽取 tier 定义/模型池/健康过滤纯逻辑，登记 fork 范围与许可证（LK-07）。

### T5 Runtime 回归确认（C-05）

- `npm test` + `bash dev-examples/manual-test/run-resume-suite.sh` + `run-stop-signal-suite.sh` + V2 三套件（确认引入三方研究性代码/依赖过程未污染主项目）。
- 本阶段**不改动 `src/`**，理论上零风险，回归作证据留存。
