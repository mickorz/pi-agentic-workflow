## 2. 任务拆解

| 任务 | 内容 | 验收锚点 |
|---|---|---|
| T1 任务控制链路 | `task_control` 意图解析（查/取消/恢复/列表）+ 用户归属过滤 + "刚才的"歧义澄清 | A13/A14 |
| T2 审批链路 | `waiting_checkpoint` → 微信审批卡片（含任务标识与内容摘要）→ `decideCheckpoint`（expectedVersion）→ 结果通知；重复/过期/跨用户审批的幂等或拒绝 | A11/A12 + SC-006 |
| T3 Outbox | `NotificationOutbox` 实体 + 投递循环 + 重试上限（LK-05：24h）+ "任务列表"主动查询补偿 | A15 + NT-006 |
| T4 中断恢复 | 用户侧"恢复"意图 → `resume(acknowledgeSideEffects)` 显式确认交互；ModelRoutingDecision 回放一致 | A16 + MR-010 |
| T5 断线自愈 | Gateway 重连：游标/去重恢复策略、停止 Bot 与取消 Run 的命令分离 | A17 |
| T6 限额 | Run 并发（沿用 maxConcurrentRuns）、消息频率、Token/成本预算（MR-011）三层限额 + 超限话术 | A18 |
| T7 重启恢复 | `.pi-wechat/` 全部状态实体的重启加载验证（映射恢复、待发通知补投、待审批不丢） | CV-004 |
| T8 审计与日志 | AuditRecord 落盘（操作者/目标/决策/版本/时间）+ 日志脱敏清单执行 | SC-006 + NFR-007 |

## 4. 风险与回滚

- 审批消息乱序/延迟到达 → 版本号（expectedVersion）+ 幂等重放是唯一防线，负例必须覆盖 A12 三种变形。
- 微信主动发送窗口受限（D-06）→ Outbox + 主动查询双通道已为预案，不在本阶段引入新机制。
- 成本统计口径（NFR-008）采集不全 → 允许 P2 先记录 tokens/耗时，成本估算延后，但不得虚构数据。
