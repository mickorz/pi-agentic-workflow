# Workflow 失败任务统计与自动诊断 —— 执行方案 V1.2（二轮评审修订版）

> 日期：2026-10-27（V1）／2026-10-28（V1.1：一轮评审 6 项修订）／2026-10-28（V1.2：二轮评审 3 阻断 + 3 完善 + 7 项验收清单）
> 来源：日报 5.2 新需求 ＋ 两轮外部评审（二轮评分 8.5/10，结论：开始开发 P0，不再扩需求）
> V1.2 修订摘要（阻断项）：
> 1. **请求层改名**：改为「请求**启动**成功率」——V1.1 定义测的是"成功启动或关联执行"，不是"最终完成"；同时新增 `unclassified` 分类（无法识别是否执行指令的消息**不排除**，单列并标注覆盖率），防路由异常无审计导致的漏统计。
> 2. **asOf 快照能力边界**：按数据源分级——只有具备完整追加历史的源支持严格 asOf；`outbox.jsonl`（重启 rm 重写只留最新）与 `manifest.json`（当前态产物）标记 `snapshot_unavailable`，**不用最终状态冒充历史快照**；从统计启用日起每日落快照，向后建立可靠历史。
> 3. **交付层加入队覆盖率**：分母从"已入队条目"改为"应通知任务"（避免"该发没入队"漏计使成功率虚高）；新增**最终通知入队覆盖率**指标；按任务去重（interrupted→resume→completed 同任务两条通知不重复计）。
> V1.2 修订摘要（完善项）：
> 4. `launched` 未 link 一律标 `unresolved`（超观察窗口也不判失败——启动超时不能证明没有真实执行，沿用 AM-P0 原则），单列"需人工核对"。
> 5. Run 层双指标：终态成功率（分母只含终态）＋ 全量状态分布并列，cancelled/running/waiting 不进成功率分母但必须可见。
> 6. 可恢复性判定收紧：`interrupted` **不自动标"可 resume"**——只报告恢复条件事实（checkpoint 是否存在、是否有副作用类节点已执行），恢复判定留人工。
> 7. "丢行率"改为**覆盖率/数量差异率**（inbox 与 chat-logs 记录语义不同，数量差异不全是丢失）。
> 定位不变：**首版只读分析**，不改线上链路，不自动修改代码，不自动重试存在副作用的任务。

## 一、目标与不做的事

**目标：**

1. 只读脚本回答三个问题：**收到的有效请求成功启动了吗？启动的 Run 跑完了吗？结果真的送到用户手里了吗？**——三层各自独立成指标，不互相冒充。
2. 全部未决态可见：unclassified / unresolved / unknown / 待确认 / 孤立 Run / 待发送——**宁可有大量"待人工"，不虚构成功率**。
3. 失败按故障阶段分类 + 归一化指纹聚合，输出可复查证据与修复优先级排行榜。
4. 从启用日起每日快照落盘，建立可靠历史；报告能回答"昨天的任务为什么失败、哪些最值得修、修复后有没有真正提高"。

**不做（本方案明确排除）：**

- 不自动修改代码、不自动重试/重放任何可能产生副作用的任务；unknown / unresolved / 孤立 Run **一律不自动判失败、不自动恢复**。
- 不新建守护进程/常驻服务/数据库/监控平台；定时交给系统调度器，脚本一次运行即退出。
- "sent" 一律表述为**发送成功率**（发送接口成功返回），不称"用户已收到率"。
- 不改 Router / Registry / 授权 / 执行器（不强制触发 WX-MOCK Gate B；验收复用 WX-MOCK 数据目录做夹具）。

## 二、现状基线（V1.1 已读码核实，V1.2 补充 RunMonitor 入队分支）

统一布局：`<dataDir>` 默认 `.pi-wechat`；全部组件挂同一 dataDir；runs 目录支持 `--runs` 显式传入。

| 数据 | 追加历史完整性 | asOf 能力 | 对本需求的作用 |
|------|--------------|----------|--------------|
| `chat-logs/YYYY-MM-DD.jsonl` | 按日文件不可变 | 严格 | 入站请求文本与用户（尽力而为可能缺行，只做辅助） |
| `inbox.jsonl` | 追加不可变（仅首见行） | 严格 | 消息量参考（**无 userId/text**，不单独分类请求） |
| `audit.jsonl` | 追加不可变、已 redact | 严格 | 请求层路由/拒绝/unknown 事件源 |
| `tasks.jsonl` | 追加式、每行带 updatedAt、末条生效 | 严格（按 updatedAt 折叠） | 任务层状态主源 |
| `run-attempts.jsonl` | 追加式末条生效、启动前预写 | 严格（按 createdAt/linkedAt） | unknown/unresolved 去重主键（attemptId） |
| `run-links.jsonl` | 追加式合并写 | 严格 | 孤立 Run 检测、终态关联 |
| `outbox.jsonl` | **重启 rm 重写，只保留各条目最新状态** | **snapshot_unavailable** | 交付层主源；历史时点状态不可重建 |
| `runs/<runId>/manifest.json` | **当前状态产物，原地更新** | **snapshot_unavailable** | Run 层当前状态与失败证据 |
| `runs/<runId>/journal.jsonl` | append-only | 严格 | 失败证据（尾部读取） |

**RunMonitor 入队规则（`run-monitor.ts` pollOnce，V1.2 实测确认）：**

- `completed` → 入队 kind=completed；`failed` → 入队 kind=failed；`interrupted` → 入队 kind=interrupted
- `cancelled` → **无入队分支**（评审正确）；`waiting_checkpoint` → 审批卡（非最终通知）
- 只扫 running/waiting_checkpoint 的 binding → 正常情况一任务一最终通知；但 **interrupted→resume→completed 会产生两条**（interrupted 通知 + completed 通知）→ 交付统计必须按任务去重
- 由上，**应通知终态 = completed / failed / interrupted**（按当前实现；业务规则变化时此表需同步更新，P0 校验脚本输出实际入队分布供比对）

关键枚举同 V1.1：TaskBinding.status 六值；AuditAction 含 intent.route/limit.reject/run.start/checkpoint.reject/am.launch.unknown/am.recovery.uncertain/outbox.giveup 等。

## 三、指标定义（三层口径，V1.2 修订）

### 3.1 请求层——「请求启动成功率」（V1.2 改名）

**衡量内容：有效执行请求是否成功启动并关联执行（产生 TaskBinding 或 RunLink）。它不是"请求最终完成率"——完成质量由 Run 层与交付层衡量，三层不混算。**

**分母 = 有效执行请求**：当日入站消息中识别为 Workflow 执行意图的（audit `intent.route` 按 messageId 去重 ∪ `url.route.direct` ∪ run-attempts 按 originMessageId 关联）。

| 分类 | 判定 | 计入启动成功率？ |
|------|------|----------------|
| 启动成功 | 产生 TaskBinding 或 RunLink | 成功 |
| 启动失败 | **有明确失败证据**：audit `run.start` outcome=failed 等 | 失败 |
| unresolved | run-attempts `launched` 超 15 分钟（TaskBinding TTL，LK-05）未 link | **否，单列**——超时不证明未执行，禁止判失败或自动重试，提示人工核对 |
| unknown | run-attempts `status=unknown`（按 attemptId 去重） | 否，单列，"需人工核对副作用" |
| 正常拒绝 | `limit.reject`、路由不匹配已回复指引、审批拒绝 | 否，单列（按设计拒绝，非故障） |
| **unclassified** | **chat-logs 有入站消息但无法关联任何 audit/run-attempts 记录** | **否，单列——不排除出报告**；其中可能藏着"路由直接抛异常、无任何审计"的漏网请求 |

请求启动成功率 = 启动成功 / (启动成功 + 启动失败)。
**覆盖率指标（P0 起 必报）：消息到审计覆盖率 = 可关联 audit/run-attempts 的入站消息数 / 入站消息总数**；unclassified 占比高说明统计存在盲区，报告显著标注。

### 3.2 Run 层——终态成功率 + 全量状态分布（V1.2 双指标）

分母口径明确化：

- **终态成功率** = manifest.status = completed / (completed + failed + interrupted)。cancelled（用户主动）、running、waiting_checkpoint **不进分母**。
- **全量状态分布**（同报告必出）：六种状态各自计数 + 孤立 Run 单列——分母构成一目了然，避免"成功率 85%"掩盖样本构成。

**孤立 Run**：runs/manifest 或 run-links 有记录但无对应 TaskBinding（启动后落盘前崩溃窗口产物）——单列清单，**不自动判失败**，标注"需人工核对"。

**asOf 边界（V1.2）**：跨日 Run 的历史时点状态按 tasks.jsonl（updatedAt）+ audit/run-attempts 事件时间严格重建；manifest 当日状态只代表"现在"，**报告中 asOf 的 Run 状态一律标注数据源为 tasks 事件流，manifest 状态仅用于 final 口径与当前快照**。

### 3.3 交付层——入队覆盖率 + 发送成功率（V1.2 双指标）

**应通知任务** = 当日到达应通知终态（completed / failed / interrupted）的任务，按 taskBindingId 去重（依据第二节 RunMonitor 入队规则；规则变化时同步更新本定义）。

| 指标 | 计算 | 说明 |
|------|------|------|
| **最终通知入队覆盖率** | 已建立最终通知记录的任务 / 应通知任务 | **防"该发没入队"漏计**：RunMonitor 异常导致连 outbox 记录都不存在时，此指标下降（仅统计已入队条目则虚高） |
| **发送成功率** | sent / (sent + failed)，**按任务去重** | pending 单列不计入；interrupted→resume→completed 的同任务两条通知取最终终态条目，interrupted 条目计入"重试链通知"单独计数 |
| 差异清单 | tasks 终态应通知 ∧ 无 outbox 记录 | 诊断信号：入队缺失，单列 runId 清单 |

未决：pending 通知单列；`outbox.giveup` 计入 failed 并单独标注（放弃投递）。

### 3.4 asOf 快照：能力分级 + 每日快照存档（V1.2 重写）

**原则：不允许用当前最终状态冒充历史快照。**

| 口径 | 数据源 | 能力 |
|------|--------|------|
| 严格 asOf | chat-logs / inbox / audit / tasks / run-attempts / run-links / journal | 按事件时间戳折叠到目标时点，可信 |
| snapshot_unavailable | outbox / manifest / result | 该源在历史时点的状态**不可重建**，报告字段标 `snapshot_unavailable`，不填推测值 |

- 报告同时输出 **asOf**（仅由严格源构成的部分）与 **final**（按归属日取当前最新状态）；两者字段名区分，头部注明口径。
- **每日快照存档**：报告脚本每次运行后把当次完整结果落 `--out/snapshots/daily-YYYY-MM-DD.json`；从启用日起，历史对比一律读快照文件（而不是重新折叠），向后建立可靠历史。启用日之前的日期不产出 asOf（标注"早于统计启用日"）。

## 四、分阶段执行

### P0：统计口径与数据验证

**交付物：`dev-examples/manual-test/wx-quality/wx-linkage-check.py`**

- 调用：`python3 wx-linkage-check.py --data <dataDir> [--runs <runsDir>] --date YYYY-MM-DD`
- 校验项（逐项输出 PASS/FAIL/WARN 与计数）：
  1. audit.target.runId ↔ tasks.runId ↔ runs 目录三向覆盖差集
  2. run-attempts.attemptId ↔ audit attemptId 一致性；`launched` 未 link → unresolved 计数
  3. run-links.runId 无 TaskBinding 的孤立 Run 数
  4. **消息到审计覆盖率**：chat-logs 入站消息可关联 audit/run-attempts 的比例（unclassified 计数与样例）
  5. **任务终态 ↔ outbox 覆盖差集**：按应通知终态（completed/failed/interrupted）比对，产出"应通知未入队"清单
  6. inbox 首见数 vs chat-logs 入站行数**数量差异率**（语义不同，仅报告差异，不下"丢失"结论）
  7. tasks.jsonl updatedAt 链完整性抽查（asOf 可行性验证）
- 输出：`linkage-YYYY-MM-DD.json` + stdout `[OK]/[WARN]/[FAIL] ...` / `=== ALL DONE ===`
- 产出决定 3.1 unclassified 识别规则是否需按真实文本校准。

**测试：`wx-linkage-check-Example.py`**（合成 fixture：三向差集/孤立 Run/unclassified/应通知未入队/断裂行/数量差异）。

### P0.5：端到端交付统计（每日质量报告主体）

**交付物：`dev-examples/manual-test/wx-quality/wx-quality-report.py`**

- 调用：`python3 wx-quality-report.py --data <dataDir> [--runs <runsDir>] --date YYYY-MM-DD [--out <目录>] [--as-of ISO时间]`
- 按第三节口径输出：
  - 头部指标：有效执行请求、**请求启动成功率**、Run 终态成功率 + 全量状态分布、**通知入队覆盖率**、**发送成功率**（asOf 与 final 两组，snapshot_unavailable 字段显式标注）
  - 未决数清单：待确认（含跨日）、unresolved（需人工核对）、unknown（attemptId 去重）、孤立 Run、unclassified（含覆盖率）、应通知未入队、pending 通知
  - 数据缺失说明（源文件不存在/断裂行数/数量差异率/早于统计启用日的范围说明）
  - 运行后落 `snapshots/daily-YYYY-MM-DD.json`
- 输出契约：`quality-YYYY-MM-DD.json/.md` + stdout `[OK] 启动 X/Y，Run 终态 X/Y，入队 X/Y，发送 X/Y` / `=== ALL DONE ===`；定时不内置（README 写调度器挂法）。

**测试：`wx-quality-report-Example.py`**：fixture 覆盖三层各分类、跨日双口径、unresolved 不判失败、unknown 按 attemptId 去重、同任务双通知去重、应通知未入队检出、outbox/manifest 的 snapshot_unavailable 标注、断裂行。

**验收标准（含二轮评审 7 项清单）：**

1. WX-MOCK 独立 data 目录执行，报告数字与场景预期一致。
2. 生产 dataDir 执行：linkage 全 PASS 或差异已解释；首个真实基线人工抽核 ≥3 种真实异常，与原始日志逐项核对。
3. 评审 7 项验收清单逐条核对：
   - [ ] 无 TaskBinding 的路由异常、启动异常能被识别或标记为 unclassified/unresolved
   - [ ] 请求启动成功率与 Run 最终成功率分开计算
   - [ ] 通知未入队、入队失败、发送失败能分别识别
   - [ ] 历史 asOf 缺乏证据时明确返回 snapshot_unavailable，不填充推测值
   - [ ] unknown、unresolved、孤立 Run 不被自动判定为失败或安全重试
   - [ ] 同一 TaskBinding 的多次状态更新和通知重试不重复计数
   - [ ] 抽核至少 3 种真实异常并与原始日志逐项核对

### P1：规则诊断与故障排行榜

**交付物：`dev-examples/manual-test/wx-quality/wx-failure-diagnose.py`**

- 调用：`python3 wx-failure-diagnose.py --data <dataDir> [--runs <runsDir>] --days 7 [--top 10] [--out <目录>]`
- 扫描：近 N 天三层全部失败与未决异常（启动失败、Run failed/interrupted、outbox failed/giveup、unknown/unresolved）。
- **两级错误归类**（同 V1.1）：

```
第一层：错误类别（按故障阶段，确定性规则）
  ROUTING_ERROR / RUN_START_ERROR / AGENT_UNKNOWN / WORKFLOW_ERROR /
  MODEL_API_ERROR（HTTP 状态码保留）/ TOOL_EXEC_ERROR / NOTIFY_ERROR / UNKNOWN

第二层：归一化指纹 = 类别 + errorCode + stage + normalizedMessage
  normalizedMessage：errorCode 保留；HTTP 状态码保留；仅数字/UUID/hash/路径归一化；sha256 前 12 位
```

- **排行榜字段**（每行一个指纹类）：失败次数、影响任务数（去重）、影响 Workflow、错误类别、证据路径、可恢复性、首次/最近出现时间。
- **可恢复性（V1.2 收紧）**：
  - interrupted → **不自动标"可 resume"**；报告恢复条件事实：checkpoint 是否存在、错误类别是否含副作用类节点（发布/扣费/写入），结论一律"需人工评估"
  - unknown/unresolved → 必须人工
  - NOTIFY_ERROR → 重试由 Outbox 机制负责，标"机制内重试"
  - 其余 failed 按类别规则表给提示，置信度首版不标高，无法确认一律"未知模式"
- 脱敏：manifest/journal 输出前基础正则脱敏（token/sk-/Bearer），只落本地 `--out`。

**测试：`wx-failure-diagnose-Example.py`**：fixture 断言——HTTP 401 与 429 不归并、同根因不同参数归同指纹、unknown 按 attemptId 去重、敏感串脱敏、interrupted 输出恢复条件事实而非"可 resume"结论。

**验收标准：**
1. 401/429/500 三类样例分成三个指纹。
2. 生产 7 天窗口产出首个排行榜，人工确认 Top1 符合直觉、影响任务数 ≤ 失败次数。

### P2：AI 根因诊断（后续，连续数天真实数据后再投入）

把 P1 脱敏故障证据喂给模型，产出原因假设、修复建议、WX-MOCK 回归测试建议。输出仅为建议，人工确认后才进 P3。

### P3：受控自动修复（暂缓）

隔离分支修复 + WX-MOCK 回归用例（场景文件与工作流同 PR）→ Gate B → 人工审批 → 合并。触发条件：P1 排行榜稳定、修复建议准确率经人工确认达标后再议。

## 六、风险与注意事项

- **chat-log 尽力而为可能缺行**：不进任何成功率分子分母；与 inbox 的差异只报"数量差异率"，不下"丢失"结论。
- **inbox.jsonl 无 userId/text**：请求分类以 audit + run-attempts + chat-logs 联合判定；无法判定归 unclassified（不排除）。
- **Outbox 重启 rm 重写**：条目保留仅清退避；历史时点状态不可重建 → snapshot_unavailable；脚本容忍读取到半行。
- **manifest 是当前态产物**：asOf 的 Run 状态一律取 tasks 事件流，manifest 仅用于 final 与当前快照。
- **一次启动尝试多条审计**：unknown/unresolved 计数一律以 run-attempts.attemptId 为准。
- **应通知终态定义绑定当前 RunMonitor 实现**：业务通知规则变化时第三节 3.3 需同步更新（P0 校验项 5 持续比对实际入队分布）。
- **unresolved ≠ 失败**：启动超时不能证明没有真实执行，禁自动重试（AM-P0 原则）。
- **"统计 ≠ 线上稳定"**：首个真实基线人工抽核 ≥3 种异常逐项核对；口径有误先修口径。
