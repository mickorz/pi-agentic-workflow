# F9 停机消息补拉能力调研（P2）

> 日期：2026-10-23 · 对应需求：dev-docs/design/2026-10-22-wechat-persistent-service.md §4 P2 F9
> 结论先行：**客户端侧机制已完备（cursor 跨重启持久化 + seen-ids 去重），重启后会自动从上次位置继续拉；
> 停机期间消息是否补拉完全取决于 iLink 桥服务端的离线保留策略——客户端代码无法回答，需按 §3 实验验证。**

## 1. 现有机制（thirdparties/pi-wechat-assistant 源码证据）

| 机制 | 位置 | 语义 |
|---|---|---|
| 消息游标 | wechat/client.ts `getUpdates`：每批拉取后 `cursor = response.get_updates_buf` 并 `saveCursor` 落盘（cursor.json） | 跨重启持久：重启后从上次位置继续，防重放历史 |
| 去重兜底 | transport-state.ts `seen-ids.json`（游标丢失/过期时防重发） | 幂等第二道防线（与 gateway Inbox 幂等第三道叠加） |
| 在线状态通知 | api.ts `notifyStart` / `notifyStop`（client 启停时调用 `/ilink/bot/msg/notifystart|stop`） | 桥知道 bot 上下线；**停机=显式通知（优雅停止）或断连（崩溃）** |

即：若桥在 bot 离线期间为其保留消息队列，现客户端**零改动**即可在重启后补拉（cursor 语义天然支持）。

## 2. 关键未知量（决定性）

iLink 桥（`/ilink/bot/msg/*` 协议）在以下两种离线形态下是否为 bot 保留消息、保留窗口多长：
1. **优雅停机**（收到 notifyStop 后）：可能主动停投/丢弃
2. **断连**（无 notifyStop，进程死亡）：可能按会话保活窗口保留一段时间

已有实测反例（设计 §1，2026-10-22）：停机期间发的翻译指令无答复、journal 无记录——至少某一种形态下不保留
（当时停机方式与窗口未记录，无法区分形态）。协议文档在客户端仓库内未覆盖此行为。

## 3. 验证实验设计（单独立项执行；需真机微信配合，~1 小时）

前置：服务 healthy（Windows 侧）。

| 实验 | 步骤 | 判定 |
|---|---|---|
| A 优雅停机窗口 | 微信发「补拉测试A」→ 5s 内 `wechat service stop` → 等 10 分钟 → `service start` → 观察 | 收到回复/journal 出现该 messageId = 优雅停机**保留** |
| B 断连窗口 | 微信发「补拉测试B」→ 立即 taskkill bot pid（无 notifyStop，PM2 会自动拉起）→ 观察 | PM2 拉起后收到 = 断连**保留**（短窗口） |
| C 保留窗口梯度 | A/B 基础上停机时长 2min / 10min / 1h 三档 | 找出保留窗口边界 |

观测：`.pi-wechat/inbox-journal.jsonl` 是否出现停机期 messageId（gateway 幂等层先于回复，最可靠）。

## 4. 结论分支与后续

- **实验通过（桥保留）**：F9 关闭——现有 cursor 机制已覆盖，无需开发；把结论补进本文档与设计文档附录。
- **实验不通过（桥不保留/窗口太短）**：F9 结论=协议层不支持，维持设计 §3「接受停机丢失」；
  可选缓解（不承诺）：开机自启（F6 已做）+ 崩溃自动拉起（F4 已做）已把不可达窗口压缩到「进程死亡→PM2 拉起」的秒级，
  剩余暴露面=计划内停机与长故障——属运维接受范围。
- 无论分支：不做客户端侧「主动补拉」开发（无协议支撑属幻想实现）。
