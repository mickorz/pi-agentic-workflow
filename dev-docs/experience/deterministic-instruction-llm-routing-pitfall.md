# 确定性指令被塞给 LLM 路由器——审批决策被置信度门限卡死

> 日期：2026-10-21 · 发现于 WX-PT Part B 真机（B02）
> 关联：src/dispatch/dispatcher.ts、src/dispatch/task-control.ts
> 关联背景：RP 线路由评测（42 样本真实 LLM 97.6%）已通过，为何真机仍翻车

## 问题现象

微信端有待审批任务时，用户回复「批准」得到：

```
置信度不足（0.6 < 0.75），请换种说法或指明工作流
```

审批链路被卡死，任务永远停在 waiting_checkpoint——LLM 路由器的置信度门限把
审批决策指令当成"看不懂的任务文本"拒掉了。

## 排查过程

1. 服务日志与审计显示「批准」走了 `intent.route`，LLM 置信度 0.6 被 0.75 门限拒掉（refuse 路径）。
2. 读 dispatcher.handleMessage：`task_control` 分发的前提是 **LLM 先分类成功**——
   `parseVerb`（确定性动词规则）排在 LLM 之后，LLM 失败则规则永远没机会执行。
3. 对比参数补齐（pendingPlan）：有挂起补参时**确定性短路**不走 LLM——审批漏了同样处理。

## 根因分析（三层）

### 1. 路由器是"上下文盲"的

`IntentRouter.plan({ text })` 的输入只有**消息文本 + Registry 候选元数据**，看不到
"该用户此刻有 N 个待审批任务"。而"批准"的意图**本质依赖语境**：

| 语境 | 「批准」的真实意图 |
|---|---|
| 有待审批项 | 审批决策（task_control） |
| 无待审批项 | 可能是任务文本的一部分（"帮我批准后写报告"） |

没有上下文，LLM 只能猜 → 低置信 → 门限拒绝。门限本身行为是对的（低置信不执行），
错的是让 LLM 处理它处理不了的问题。

### 2. 架构分层用反了（主因）

IR-008 原文："查询/取消/批准/拒绝/恢复等任务控制操作**必须走 Task Control**，而不是
将其作为新的任意 Workflow"。但实现做成了：

```
错误分层（原实现）：消息 → LLM 分类为 task_control → 才交给 parseVerb 规则
正确分层（IR-008 本意）：消息 → parseVerb 确定性规则命中 → 直接 TaskControl；LLM 只兜规则外的模糊文本
```

**确定性指令被塞给概率性路由器当守门员**——LLM 一失败，后面本来能百分百处理的
确定性规则根本没机会执行。讽刺的是参数补齐（pendingPlan）当时就做对了（短路），
审批漏了同样的处理。

### 3. 为什么昨天的路由评测（97.6%）测不出来

RP 线评测是**单轮、无上下文**回放（evaluate.ts 逐条独立跑）。42 条样本里
"批准"只是普通文本，没有会话状态注入——**语境依赖型意图**（审批决策/参数补充）
天然在路由评测盲区。这不是评测做错了，是评测维度的边界：

> **路由质量 ≠ 上下文调度正确性**，两个维度。

## 解决方案

1. **dispatcher 直通**：`hasPendingApproval(userId)` 为真时，决策动词/纯数字直接进
   TaskControl（不经 LLM；confidence=1，reason 标注"审批决策直通"）。
2. **体验**：歧义澄清改**序号制**（回复「批准 1」免复制 tb- 长 ID；tb- 精确指定仍支持）。
3. **批量**：`decideMulti` 支持「批准 2 拒绝 1」一条消息多段操作，序号按澄清列表
   **快照**解析（防执行后序号位移歧义）。
4. **直通面刻意收窄**：仅 approve/reject 动词 + 待审批语境（status 正则 `/怎么样|查询/`
   太宽，全直通会劫持正常任务文本如"查询 Redis 用法"）。

## 结论

不是路由功能不行——它解决"开放文本 → 选哪个 workflow + 抽参数"很擅长（97.6% 可证）。
但**指令类意图（批准/拒绝/取消/序号选择）是确定性规则的地盘，不该过 LLM**。
正确分层：**规则优先短路，LLM 兜模糊**。

## 预防/注意事项

- 新增意图类型时先问：**规则可确定性识别吗？有上下文依赖吗？** 两者任一为真 →
  走确定性短路，不过 LLM。
- 路由评测样本补维度：`channel` 之外加"会话状态前提"字段（如 `pendingApproval: true`），
  语境依赖型意图才可回归。
- 正则字符类陷阱：`tb-[0-9a-zA-Z]+` 不含连字符，含 `-` 的 ID 会截断（tb-run-c → tb-run）；
  ID 字符类永远写成 `[0-9a-zA-Z-]` 或按真实格式精确声明。
