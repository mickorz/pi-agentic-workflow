# 确定性指令被塞给 LLM 路由器——审批决策被置信度门限卡死

> 日期：2026-10-21 · 发现于 WX-PT Part B 真机（B02）
> 关联：src/dispatch/dispatcher.ts、src/dispatch/task-control.ts

## 问题现象

微信端有待审批任务时，用户回复「批准」得到：`置信度不足（0.6 < 0.75），请换种说法或指明工作流`——
审批链路被卡死，任务永远停在 waiting_checkpoint。

## 排查过程

1. 服务日志与审计显示「批准」走了 `intent.route`，LLM 置信度 0.6 被 0.75 门限拒掉（refuse 路径）。
2. 读 dispatcher.handleMessage：`task_control` 分发的前提是 **LLM 先分类成功**——
   `parseVerb`（确定性动词规则）排在 LLM 之后，LLM 失败则规则永远没机会执行。
3. 对比参数补齐（pendingPlan）：有挂起补参时**确定性短路**不走 LLM——审批漏了同样处理。

## 根因

**架构分层用反**：IR-008 要求任务控制操作"必须走 Task Control"，但实现把 LLM 当守门员，
确定性规则当后卫。且 IntentRouter 是上下文盲的（输入只有文本+候选元数据，看不到
"该用户有 N 个待审批项"），意图本质依赖语境的「批准」只能靠猜 → 低置信 → 卡死。

深层教训：**指令类意图（批准/拒绝/取消/序号选择）是确定性规则的地盘，不应过 LLM**；
LLM 路由器只兜规则覆盖不了的开放文本。单轮无上下文的路由评测（97.6%）测不出此类
语境依赖型意图——路由质量 ≠ 上下文调度正确性。

## 解决方案

1. dispatcher 直通：`hasPendingApproval(userId)` 为真时，决策动词/纯数字直接进 TaskControl
   （不经 LLM；confidence=1，reason 标注"审批决策直通"）。
2. 体验：歧义澄清改**序号制**（回复「批准 1」，免复制 tb- 长 ID；tb- 精确指定仍支持）。
3. 批量：`decideMulti` 支持「批准 2 拒绝 1」一条消息多段操作，序号按澄清列表**快照**解析
   （防执行后序号位移）。
4. 直通面刻意收窄：仅 approve/reject 动词 + 待审批语境（status 正则 `/怎么样|查询/` 太宽，
   全直通会劫持正常任务文本如"查询 Redis 用法"）。

## 预防/注意事项

- 新增意图类型时先问：**规则可确定性识别吗？有上下文依赖吗？**两者任一为真 → 走确定性短路，
  不过 LLM。
- 路由评测样本补维度：`channel` 之外加"会话状态前提"字段（如 pendingApproval: true），
  语境依赖型意图才可回归。
- 正则字符类陷阱：`tb-[0-9a-zA-Z]+` 不含连字符，含 `-` 的 ID 会截断（tb-run-c → tb-run）；
  ID 字符类永远写成 `[0-9a-zA-Z-]` 或按真实格式精确声明。
