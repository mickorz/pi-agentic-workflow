# 确认点 2 后的正确收尾顺序：读用户保存结果，不要自己另开浏览器导出（2026-11-24 黎曼猜想篇）

## 问题现象

黎曼猜想篇 G.5 确认点 2：用户在自己 Chrome 的预览工作台里改了章题、点保存、点了「导出渲染 HTML」，然后在聊天回复确认。agent（我）收到确认后没有先检查用户保存的产物，而是直接用 chrome-devtools MCP 另开一个 Chrome 实例、注入 token、准备自己导出 layout.html——被用户当场指出："为什么你没有按照流程读取我保存的文件，而是自己打开一个 chrome"。

## 根因

1. **工作台内已有动作的未检查**：用户在预览内的"保存"会写回文章目录 md，"导出渲染 HTML"会生成 layout.html。确认点 2 的正确解读是"用户在工作台完成编辑+导出后聊天确认"，agent 收到确认后第一件事是**检查文章目录的产物状态**（正文 mtime 是否变化、layout.html 是否已存在且比正文新），而不是重做导出动作。
2. **通道惯性误用**：chrome-devtools MCP 是上一轮排查多 Chrome 实例 E_ENV 时用过的工具，到收尾时顺手复用，没有回到流程文本（"先确保工作台已点导出……检查 layout.html 比正文新"）确认自己该做什么。
3. **另一个隐藏收益被错过**：先读用户保存的正文才能发现用户改动（本例：第 2 章章题删掉了"小学生也能听懂"），改动需要重跑 check_state 并更新 humanizer 缓存——agent 若直接 publish 会跳过这些。

## 正确流程（确认点 2 收到"确认"后的标准动作）

1. **检查正文**：`ls -la` 看 md mtime；若变化，diff/通读用户改动，重跑 check_state（digest/图片引用可能变化），humanizer 缓存中对应章 hash 更新重扫。
2. **检查 layout.html**：已存在且比正文新 → 直接用，不重新导出；不存在或比正文旧 → 才需要补导出（优先让用户在工作台点按钮，或 agent 用浏览器通道代办并说明）。
3. **publish**：用用户的 layout.html（它基于用户确认后的最终正文）。
4. **停台**：杀自己起的 pi-workflow web；提醒用户关自己 Chrome 里的预览标签页。
5. agent 自己开的辅助浏览器实例（chrome-devtools MCP 等）用完随手关，不留到确认后。
