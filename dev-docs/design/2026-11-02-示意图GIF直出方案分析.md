# 示意图 GIF 直出方案分析（流程图/结构图/架构图脱离 ChatGPT 生成）

- 日期：2026-11-02
- 背景：公众号配图管线（gzh-article-craft D/E/F 阶段）目前所有配图统一走"提示词 → image-use（ChatGPT web）→ 光栅图"。用户提出：流程图/结构图/架构图类不该走 ChatGPT，应调用 `~/.claude/skills/drawskills` 直接生成 GIF 动图，用动图表达流程、结构与架构。
- 结论先行：**方向正确，建议"分引擎分图型"路由，而不是全部切走**。概念/拟人类（封面、3D 信息图）保留 ChatGPT；流程/状态机/架构/时间线/循环类改走 drawskills 直出（静态走 mermaid/handsvg，动图走 livepanel→ffmpeg 转 GIF）。本机依赖全部就绪。

---

## 一、现状与问题

现状链路：`image-prompts.json`（含 diagram_type）→ executor → provider `image-use` → ChatGPT web 生图 → `imgs/NN-*.png`。

对示意图类（流程/结构/架构）的四个失真点：

1. **文字不可靠**：图像模型渲染节点标签易错字/漏字，因此才需要 expected_text 审查门 + 人工核对——直出方案下这个问题天然消失（渲染器输出的文字是精确注入的）。
2. **结构保真度低**：箭头方向、节点从属、连线交叉是图像模型的弱项，架构图常"看着像但逻辑错"，需要懂行的人逐张核对。
3. **非确定性 + 有成本**：同一提示词两次生成结果不同；走 ChatGPT web 消耗订阅额度与时间（DeepSeek 篇 5 张跑了 4 分钟）。
4. **无动画能力**：流程/闭环类最适合"数据流动起来"的表达，光栅静态图表达不了。

## 二、drawskills 能力盘点（~/.claude/skills/drawskills v0.4.2）

| 引擎 | 输出 | 依赖 | 适配本需求的判断 |
|---|---|---|---|
| mermaid | .mmd → SVG/PNG/ASCII（vendored 本地渲染，15 主题，无需浏览器） | Node ≥16（本机 v24 ✓） | 流程图/时序/状态机静态直出的**首选**：语法简洁、确定性、可版本控制 |
| handsvg | 直接写 SVG（draw.io 风格 + 完整连线） | 无 | 架构图静态直出备选；布局需模型手排坐标，质量看运气 |
| drawio | XML → SVG/PNG | drawio MCP server | 本机未接 MCP，暂不依赖 |
| excalidraw | JSON | 无 | 手绘风，公众号场景少用 |
| **livepanel** | JSON config → **mp4 / HTML / PNG 帧**（终端监控面板风动画，确定性渲染，可 seek） | Python3 纯标准库 + Chrome（**Windows 有专用 render_win.py/check_win.py**，CDP 驱动）；mp4 另需 ffmpeg | **动态架构/闭环图的唯一引擎**；官方定位即"用户要的是活的架构图——视频、GIF 式循环" |

关键事实：livepanel **不直接输出 GIF**，输出 mp4（可加静音 AAC 轨，部分聊天应用将无轨 mp4 当 GIF）或 PNG 帧；要 GIF 需 mp4/帧 → ffmpeg 转制（本机 ffmpeg 9.0 ✓）。

本机依赖核查：chrome-use 1.5.268 ✓、Chrome ✓（C:\Program Files\Google\Chrome\Application\chrome.exe）、Node v24 ✓、Python 3.14 ✓、ffmpeg 9.0 ✓、render_win.py（Windows 纯标准库 CDP 版）✓。**全链路就绪，零新增安装。**

## 三、GIF 技术路线

```
image-prompts.json（diagram_type + diagram_engine + diagram_source）
        │
        ├─ mermaid 静态：.mmd → vendor/pretty-mermaid render.mjs → PNG(1200w) → imgs/NN-xxx.png
        │
        └─ livepanel 动态：JSON config → render_win.py → mp4
                              → ffmpeg（palettegen 两段式）→ GIF → imgs/NN-xxx.gif
```

GIF 体积控制（公众号单图上限 10MB，且正文 GIF 自动循环播放）：

- 时长 6-10s 循环、宽度 640-800px、帧率 10-12fps，palettegen/paletteuse 两段式转制，典型落点 2-6MB
- livepanel 的确定性渲染（window.seek(t)）保证每次重渲结果一致——回填/重生成无抖动

注意：**mp4 不能直接进公众号正文**（正文不支持视频标签，视频要走素材库视频消息），所以 GIF 转制是必须步骤，不是可选项。

## 四、管线集成设计

### 路由规则（按 diagram_type 分流，ChatGPT 只管它擅长的）

| diagram_type | 引擎路由 | 输出 | 理由 |
|---|---|---|---|
| 封面 / 3D信息图 | image-use（ChatGPT）不变 | PNG | 拟人场景、质感光效，图像模型的主场 |
| 概念信息图（含对比图） | image-use 不变（或后续迁 handsvg） | PNG | 同上 |
| 流程图 / 循环图 | mermaid 静态 或 livepanel 动态 | PNG / **GIF** | 步骤流动感是动画的价值区 |
| 状态机 | mermaid（stateDiagram） | PNG | 语法原生支持 |
| 架构图 | handsvg / mermaid 静态；要动效则 livepanel | PNG / GIF | livepanel 仅架构类动态图 |
| 时间线 | mermaid（timeline）或代码直出 | PNG | — |

### image-prompts.json 增量字段（向后兼容）

```json
{
  "id": "architecture",
  "diagram_type": "架构图",
  "diagram_engine": "livepanel",          // 新增：mermaid | handsvg | livepanel；缺省=走 image-use
  "diagram_source": { "config": "..." },  // 新增：mermaid 源码 / livepanel JSON config
  "expected_text": ["Router", "Worker", "Watchdog"],  // 保留：渲染后用视觉工具核对（确定性渲染下应恒过）
  "filename": "04-Super-agent架构.gif"
}
```

- executor 新增 provider `diagram`：按 diagram_engine 调 mermaid 渲染或 livepanel+ffmpeg；产物直接落 `imgs/`，manifest 照常记 status/evidence
- **expected_text 门保留**：直出方案下文字是精确渲染，此门从"抓错字"退化为"抽查确认"，成本趋零但保险仍在
- publish.py：公众号素材接口 type=image 本身支持 gif 上传，**需在入箱时实测一次**（列为待验证项；若 thumb 或压缩策略对 gif 有额外限制再适配）

### 与现有资产的关系

- 仓库内已有 `.pi/skills/diagram-design`（HTML/SVG 编辑风多类型图表）：与 drawskills 定位重叠。取舍建议——**静态图优先 mermaid/handsvg（轻、确定性、无浏览器依赖）；需要编辑级排版或 HTML 交互再用 diagram-design；动图只有 livepanel 一条路**。三者不互斥，按 diagram_engine 字段选。
- drawskills 在 `~/.claude/skills`（Claude 侧技能），executor（Node）只调用其 vendor 渲染器与脚本，不加载其 SKILL.md——管线依赖的是工具，不是技能编排。

## 五、风险与权衡

| 风险 | 影响 | 缓解 |
|---|---|---|
| livepanel 视觉风格是"终端监控面板"（terminal-dark/light-pastel），与账号 3D 蓝白色板不一致 | 系列图风格分裂 | ①接受差异（动图 vs 静图本就不同质感）②config 主题色可改（theme.preset 自定义）③封面/概念图仍走 ChatGPT 保持系列识别度 |
| GIF 体积超 10MB | 公众号上传失败 | 时长/宽度/帧率三参数控制 + ffmpeg palettegen；脚本内置体积检查，超限自动降规格重转 |
| livepanel 只支持架构类动态图 | 循环/流程类动图要绕 | 闭环类可用 architecture 数据流变体表达；纯 flowchart 动画需求评估成本后决定是否值得扩展 |
| 双管线维护成本 | executor、审批文档、对账逻辑都要认 gif | provider 抽象统一 manifest 记录；对账已按文件名白名单（gif 需加入 IMG_REF 正则白名单——现正则只认 jpg/png，**列为必改项**） |
| 文章正文引用语（"如图"）对动图描述 | 静态描述词不匹配动图 | 写作规范补一条：动图配文写"动图展示……的流转" |

**必改项（不管选哪条路）**：`IMG_REF` 正则/check_state/normalize 当前只认 `jpg/png`（pitfalls #1），引入 `.gif` 前需全链放行 gif 扩展名。

## 决策记录（2026-11-02 用户拍板）

- **采纳分图型路由**：流程/结构/架构/状态机/时间线类脱离 ChatGPT，走 drawskills 直出；封面与 3D 概念图保留 image-use
- **GIF 输出升级为 drawskills 内建能力**：不把“mp4/PNG 帧 → ffmpeg 外部转制”作为正式链路，而是**改造 drawskills 的 livepanel 引擎支持 GIF 直出**（新增 `--format gif` 类输出：内部完成帧序列 → ffmpeg palettegen 两段式封装，用户侧只见一次调用）；外部 ffmpeg 命令降级为兜底路径
- 相应调整：阶段 2 从“搭转制链路”改为“改造 livepanel 支持 GIF 直出 + 体积控制内置”；`render.py`/`render_win.py` 两版同步支持，保持跨平台一致
- **livepanel 主题默认值：light-pastel（浅色）**（2026-11-02 补充拍板）：公众号文章为白底阅读场景，浅色主题与正文视觉一致；terminal-dark 仅在需要暗色风格的特殊图型时显式指定。该默认值写入管线生成的 livepanel config（theme.preset 字段），不属于 drawskills 引擎层默认值的修改
