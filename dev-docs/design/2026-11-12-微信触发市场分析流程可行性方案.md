# 微信触发市场分析流程设计方案 V2（评审修订版）

- 日期：2026-11-12（V1 初稿 → 同日 V2 评审修订，评审意见全部采纳，三个 P0 已对照源码核实）
- 需求：在公司等屏蔽渠道的网络环境，向微信 bot 发"分析目标"，流程在本机（家庭 Mac）自动完成三渠道市场分析，报告落 Obsidian `60_Workspace/写作/市场分析/`，微信回执；人工确认后才可进入创作。
- **V1 范围限定（评审定案）**：只做「输入主题 → 自动研究 → Obsidian 报告 → 微信告知 → 人工确认」闭环；不自动衔接 gzh-article-craft 创作或发布。

## 0. 架构（V2：增加确定性前缀路由、预检、质量验证与研究状态机）

```
手机微信（任意网络）
  → wechat-bot（本机 pm2）
  → 路由双通道：
      ①确定性前缀：「市场分析: <主题>」→ 直接 workflowId=market-analysis + topic（不经 LLM，仿 url-route 先例）
      ②自然语言（"帮我研究一下 X 的市场"）→ IntentRouter LLM（0.75 置信门限），命中注册项才启动
  → market-analysis workflow（riskLevel=write + capabilities 含 obsidian-write）
      预检（relay/Chrome/渠道降级矩阵）→ 采集（三渠道适配器，单渠道失败跳过并标注）
      → 标准化（样本 Schema）→ 质量验证（数量/证据分级/覆盖率）→ content-intelligence 分析（九段报告）
      → Obsidian 写入（路径受限 + 原子写 + 幂等）→ 回执
  → 研究状态机（analysisId 持久化于状态文件，不依赖会话 TTL）
  → 微信回执（研究编号 + 样本覆盖 + 编号方向 + 确认指令）
```

## 1. P0 修订（对照源码核实）

### P0-1 权限：write 声明 + autoApprove 白名单（不走 read-only 绕过）
- workflow 注册声明 `riskLevel: "write"` + `capabilities: ["obsidian-write"]`（registry.ts L45 校验会拒绝 read-only+写能力的组合，已核实）
- 微信自动执行采用服务端 `autoApprove` 白名单（task-control-facade.ts L252，启动期 `--auto-approve` 显式声明，预检全过后人闸豁免、执行走 authorized 同路径，已核实）
- **路径限定**：autoApprove 是 workflow 级白名单，"只写市场分析目录"由 workflow 自身保证——写入器沿用 archive_inspire.py 的硬约束模式（ensure_under commonpath 校验 + 无符号链接 + 原子替换），目录白名单 `60_Workspace/写作/市场分析/`
- 不启用 autoApprove 的环境（如公司侧镜像部署）自动回落微信批准步骤

### P0-2 研究状态机：完成 ≠ 确认
| 状态 | 含义 | 触发 |
|---|---|---|
| `RESEARCH_RUNNING` | 采集中 | 受理成功 |
| `RESEARCH_READY` | 报告落盘+质量检查过 | run 正常完成（**不代表方向已批准**） |
| `RESEARCH_CONFIRMED` | 用户确认方向 | 微信「确认 MA-xxx 方向N」 |
| `RESEARCH_FAILED` | 无法交付有效报告 | 渠道全断/样本低于下限 |

- 状态持久化于 `<vault>/60_Workspace/写作/市场分析/.state/<analysisId>.json`，**解决 15 分钟会话 TTL 与 10-30 分钟研究时长的冲突**——确认/重跑指令凭 analysisId 关联，不依赖临时会话
- content-intelligence 第 7 步硬停语义不变：RESEARCH_READY 只是"报告可读"，进创作必须 RESEARCH_CONFIRMED

### P0-3 确定性前缀路由
- `市场分析: <主题>` / `选题分析: <主题>` 前缀直接解析（同 videodigest 的 URL 确定性路由层，**关键词注册仅服务 LLM 检索候选，不承担确定性触发**，评审指出的 0.75 门限已核实）
- 自然语言表达继续走 IntentRouter，保留灵活性

## 2. P1 修订（全部采纳）

| 项 | V2 设计 |
|---|---|
| 采集脚本化 | **T0 先行**：三平台各跑通一条真实采集链路并记录失败模式，是全方案最大技术不确定性；chrome-use 实测 ≠ 无人值守脚本稳定 |
| 报告完整性分级 | 完整（≥20 或达配额 80%）/ 部分（渠道降级或样本不足，回执与报告 frontmatter 标注 `partial_coverage`）/ 失败（样本 <10 或渠道全断） |
| 研究权重 | 默认沿用四档 30/30/30/10（含"其他"）；用户显式限定平台时按指定平台重新分配 |
| 幂等键 | `analysis_key = 规范化主题 + 平台集 + 权重规范版本 + 日期`；重发同键 → 回执已有报告；「重跑 MA-xxx」→ 强制新 analysisId |
| Chrome 互斥 | 浏览器采集加全局文件锁（复用 `.vd/locks` open(wx) 模式），与生图/其他采集任务互斥，防多任务抢同一 Chrome |
| 报告事实源 | **单一事实源 = Obsidian 市场分析/**；仓库不再写 research/ 镜像（避免双源漂移）；样本证据件仍入仓库 `content-intelligence/samples/`（引用路径写入报告） |

## 4. 依赖与降级矩阵（V1 保留，微调）

| 场景 | 行为 |

| 阶段 | 任务 | 验收 |
