# 公众号批量生图接入需求文档（V1）

- 日期：2026-10-23
- 状态：需求草案（待技术执行方案评审）
- 目标仓库：`mickorz/pi-agentic-workflow`
- 建议落点：`dev-docs/planning/公众号批量生图接入需求文档（V1）.md`
- 候选依赖：[@amaster.ai/pi-image-gen](https://pi.dev/packages/@amaster.ai/pi-image-gen)
- 优先级：P0/P1，优先完成真实公众号业务闭环

## 1. 背景与问题

当前公众号文章的内容生成、图片匹配插入、元数据维护和发布流程已基本自动化，但插画仍需要人工逐条复制提示词、在网页生图、下载并按章节归档。每篇文章通常需要多张正文图和封面图，操作重复、耗时且易遗漏。

现有能力（以当前仓库为准）：
- `PiAgentAdapter` 使用 `createAgentSession()`，并对可用工具实施白名单管理；
- `article_insert_images_meta.js` 扫描文章 `imgs/` 目录，将图片映射到章节，更新 Markdown 和 `article.yaml`；
- 公众号发布工作流已经接入现有审批与发布流程。

**缺口：** 从“已确定的插画提示词”到“本地可用图片文件”的可靠、可恢复的自动执行步骤。

## 2. 目标与非目标

### 2.1 V1 目标

G1. 给定文章目录和结构化插图清单，自动逐张调用图像模型生成图片。

G2. 将实际图片文件存入文章目录的 `imgs/`，输出可被现有插图流程消费的稳定路径。

G3. 单张失败不会丢失其他成功结果；允许失败补跑、中断续跑、跳过已成功图片。

G4. 在工作流执行日志和最终报告中准确呈现图片生成状态，不虚报成功。

G5. 从 CLI 独立运行后，可被微信任务路由或文章流水线调用；不破坏现有内容生成及发布逻辑。

### 2.2 非目标

- V1 不开发浏览器自动点击 Gemini 网页；
- 不做多模型智能路由、动态按图选择模型；
- 不做多任务并发、分布式队列或跨机器任务抢占；
- 不做自动视觉美学打分或无人工确认的发布决策；
- 不要求像素级风格一致性；
- 不重构现有文章插入、审批、发布系统。

## 3. 典型场景

**S1 批量生图：** 用户为一篇 9 个术语章节的科普文章准备好插图提示词，在微信发送“给这篇文章生成所有图片”，系统完成生图并反馈图片数量和路径。

**S2 失败续跑：** 第 6 张图片 API 超时，前 5 张成功，后续视运行策略继续或停止；重新执行只处理失败、未开始或明确要求重做的项目。

**S3 重生成指定图片：** 用户表示“第 3 张不好，重生成”，仅该图片被重新调用模型，原有效图片暂时保留，生成结果作为新候选，经过确认后才切换有效版本。

**S4 下游集成：** 图片全部就绪后调用现有 `article_insert_images_meta.js`，检查无缺图后进入已有的发布审批流程；生图阶段本身不得直接发布。

## 4. 输入输出契约

### 4.1 输入

必填：`article_dir`（文章目录）；该目录内应存在文章正文和一份结构化生图清单。

可选：`manifest_path`、`only_ids`（选定图片）、`retry_failed`（默认 true）、`force_regenerate`（默认 false）、`max_retries`（默认 2）、`continue_on_error`（默认 true）、`dry_run`（默认 false）、`style_reference`（本地参考图，可选且模型须支持）、`model_config_profile`（V1 可只支持单一固定配置）。

输入清单建议规范化为 `image-prompts.json`，字段：
- `version`: 契约版本 `1`；
- `article_id`: 稳定文章标识；
- `style_prefix`: 所有插图共同使用的风格约束；
- `items[]`: `{ id, kind, heading, prompt, filename }`。
- `id` 在单篇内唯一且长期稳定，例如 `cover`、`term-01`；`kind` 为 `cover` 或 `body`；`heading` 是原文章节标题（封面可空）；`filename` 是期望文件名且仅允许安全相对文件名。

如果现有产物只有 `image-prompts.md`，先通过一个独立的解析/转换步骤生成 JSON；V1 生图执行器不靠 LLM 每次重新解释自由格式 Markdown，以避免重复运行时清单发生漂移。

**示例：**

```json
{
  "version": 1,
  "article_id": "ai-terms-04",
  "style_prefix": "统一的小王子童话插画风格，暖色柔光，不要文字。",
  "items": [
    {
      "id": "cover",
      "kind": "cover",
      "heading": "",
      "prompt": "九个 AI 模型术语的封面构图",
      "filename": "cover.png"
    },
    {
      "id": "term-01",
      "kind": "body",
      "heading": "## Transformer（转换器架构）",
      "prompt": "用连接起来的星球表现 Transformer",
      "filename": "01-transformer.png"
    }
  ]
}
```

### 4.2 输出

文件约定：
- 正文插图：`<article_dir>/imgs/<filename>`；
- 封面图：`<article_dir>/cover.<实际扩展名>`，与现有插图流程兼容；
- 状态清单：`<article_dir>/image-manifest.json`；
- 不修改原有 `image-prompts.json` 和正文 Markdown（插图由下游处理）。

`image-manifest.json` 每个条目至少记录：`id`、`prompt_hash`、`status`（`pending/running/succeeded/failed`）、`attempts`、`model`、`provider`、`path`、`mime_type`、`error_code`、`updated_at`；可扩展 `active_path`、`candidate_paths`、`reference_hash`。

工作流标准返回值：

```json
{
  "ok": false,
  "article_dir": "/path/to/article",
  "total": 10,
  "succeeded": 8,
  "failed": 1,
  "pending": 1,
  "manifest_path": "/path/to/article/image-manifest.json",
  "generated_paths": [],
  "failed_ids": ["term-06"],
  "pending_ids": ["term-07"]
}
```

`ok=true` 当且仅当全部**必需**图片通过文件校验且处于成功状态。整体失败不能掩盖局部成功。

## 5. 核心功能需求（EARS）

**FR-01 清单校验**  
WHEN 生图任务启动时，系统 SHALL 检查文章目录、清单版本、图片 ID 唯一性、提示词非空、路径安全性以及章节对应关系；校验失败 SHALL 在调用 API 前停止并输出具体问题。

**FR-02 模型接入**  
WHEN 单图执行时，系统 SHALL 通过独立 `ImageGeneratorAdapter` 调用配置好的图片 Provider，返回实际图片路径、格式及模型标识；不得依赖模型文本回复宣称“已生成”。

**FR-03 文件保存**  
WHEN Provider 返回图像时，系统 SHALL 检查文件存在、可解码、格式受支持且大小合理，并保存至指定文章目录；不得静默覆盖已确认的有效图片。

**FR-04 顺序批量执行**  
WHEN 存在多个待处理条目时，系统 SHALL 按清单顺序逐个执行，V1 默认并发度为 1，并在每张结束后持久化执行状态。

**FR-05 幂等续跑**  
WHEN 重新执行同一任务时，系统 SHALL 跳过 `prompt_hash`、模型配置和参考图指纹未变化且输出文件仍有效的成功条目；任一关键输入变化 SHALL 标记条目需重新生成，而不是复用旧结果。

**FR-06 重试**  
IF 生图调用发生可恢复失败（如超时、限流或临时服务错误），系统 SHALL 在有界次数内重试，并记录尝试次数；认证失败、无效参数、余额不足等非暂时错误 SHALL 快速失败。重试必须受 Provider 限流约束。

**FR-07 部分失败**  
IF 某张图片最终生成失败，系统 SHALL 记录错误并按照 `continue_on_error` 决定是否继续后续图片，不得将失败图片标为成功。

**FR-08 取消和恢复**  
WHEN 任务被取消或进程重启时，系统 SHALL 保留已完成的有效图片；启动时将无有效结果的遗留 `running` 条目视为待核验状态，核验后再重试，不假定远程任务未执行。

**FR-09 单张重生成**  
WHEN 用户明确选择某个图片 ID 重做时，系统 SHALL 仅重生成该条目，保留现有有效图，新图片成功校验后方可更换有效版本；失败不破坏原图。

**FR-10 现有插图集成**  
WHEN 所有必需图片生成并验证成功时，系统 SHALL 允许调用现有 `article_insert_images_meta.js`；图片未完成时 SHALL 阻止自动进入无条件发布路径，但允许查看报告和手动处理。

**FR-11 任务可观测性**  
WHEN 任务执行时，系统 SHALL 记录文章 ID、图片 ID、状态、模型、尝试次数、耗时和经过脱敏的错误摘要；API Key、带签名 URL、原始认证响应不得进入日志。

**FR-12 权限审批**  
WHEN 微信发起付费 API 生图或写入图片时，系统 SHALL 复用现有风险等级与执行授权机制，在执行前得到相应授权；生图结束不得自动绕过现有公众号发布审批。

## 6. 技术边界与建议

### 6.1 模块边界

建议分两层：
1. 通用层 `ImageGeneratorAdapter`：负责生成、取消、统一结果与错误、供应商配置；优先验证复用 `@amaster.ai/pi-image-gen` 导出的 `generateImage()`。注意核验已发布 npm 包的 exports、版本、依赖与真实执行效果。
2. 业务层 `article-image-generate.js`：负责提示词清单、图片 ID、顺序执行、Manifest、重试续跑与文章目录约定。

**不要**在业务 Workflow 内写死特定 Gemini/OpenAI HTTP 请求，也不要为了生图直接修改既有的只读 `explore` 工具白名单。

### 6.2 现有架构兼容风险

当前 `PiAgentAdapter` 创建 Agent 会话时显式提供工具白名单（`general` 为 `read/bash/edit/write`），因此安装 Pi Extension 不等于 Workflow Agent 可直接使用 `image_generate`。建议优先走确定性 Adapter 接口；若确需 Extension 工具桥接，应单独设计特定权限 Profile，验证 Extension 加载与工具执行机制。

候选包中的 `image_generate` 工具模型由包配置指定，工具本身不接收任意模型参数；V1 可接受固定模型，未来动态路由再抽象。

### 6.3 状态与并发

- 每张图片完成后原子写入或通过可恢复事务更新 Manifest；
- 同一文章 V1 不允许两个生图任务并行修改相同 Manifest 或有效图片；
- 采用文章级锁或复用已有文章锁机制，但需要检查现有锁与生图过程的临界区，避免无谓地长期锁定整个文章业务；
- 不引入跨机器分布式锁；云同步 Vault 的多机同时写入属于 V1 明确禁止场景；
- `dry_run` 只检查计划，不产生文件写入、模型调用或扣费。

## 7. 非功能需求

- **跨平台：** Windows、macOS 均可运行；不要依赖 PowerShell 专有命令来完成生图核心链路。
- **可恢复：** 中途崩溃后可根据 Manifest 与实际文件核验续跑。
- **安全：** 路径必须约束在指定文章目录；禁止 `../` 路径逃逸和未经授权的外部文件覆盖。
- **成本：** 默认每图最多 2 次自动重试（即首次 + 最多 2 次）；报告调用次数和可获得的费用信息，不捏造精确费用。
- **兼容：** 不破坏已有 `imgs/`、`cover.*`、`article.yaml`、文章插图与发布工作流。
- **可测试：** 提供 Fake Provider，无真实 API 费用即可验证大部分契约。

## 10. 最终用户体验

用户在微信发送：**“给第四期 AI 术语文章生成全部插图。”**

系统识别文章并完成已有授权后：
1. 定位文章目录和插画提示词清单；
2. 检查计划和已有图片；
3. 按顺序生成缺失图片并存到指定目录；
4. 记录每张图片的状态，失败重试；
5. 将图片交给现有插图工作流；
6. 返回结果：“共 10 张，成功 10 张，已插入正文，文章已准备就绪；发布需按原流程确认”。

如发生失败，返回失败的图片 ID、简要原因和下一次续跑方式，不触发自动发布。

## 11. V1 完成定义（Definition of Done）

- 一次 CLI 命令可完成单篇文章的批量生图；
- 已成功图片重复执行不产生额外费用；
- 部分失败不丢失已有图片，可单张补跑；
- 图片与文章章节具有可追踪的一一对应关系；
- 能复用已有 `article_insert_images_meta.js` 和文章发布审批链；
- Fake Provider 测试覆盖验收矩阵，至少做一次真实 Provider 端到端手动验收；
- 记录候选依赖版本、运行环境、真实调用方式与已知限制。

## 12. 待执行方案确认的问题

1. 当前文章的图片提示词真实存储在哪个文件、采用什么格式？确定迁移到 `image-prompts.json` 的转换规则。
2. 使用哪家 Provider 和具体生图模型进行首个真实 API 验证？需确保独立 API 凭证与调用额度。
3. 需要复用哪一套现有文章级锁与审批机制？明确锁作用域、接管规则和写入边界。
4. 候选包发行版本是否稳定导出 `generateImage()`，其 Peer Dependencies 是否兼容目前采用的 `@earendil-works/pi-coding-agent`？
5. 用户在微信中如何明确指定文章目录或文章 ID，以避免路由到错误文章？

以上问题由 P0 验证确定，不阻塞需求文档先行评审。
