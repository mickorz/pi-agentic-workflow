我对照了你上传的《生图链路与提示词现状梳理》、压缩包里的 9 篇参考资料，以及 GitHub 上的 `mickorz/image-gen-stage2` 分支。

我的核心判断是：

你现在不需要重做生图执行器，最值得优化的是它前面的「视觉设计与提示词生成模块」。

现有工作流已经解决了许多工程问题：试生成、人工确认、费用控制、批量生成、单张重做、断点恢复。这些应该保留。现在要解决的是另外三个问题：

1. 每篇文章怎么自动选择合适的视觉表达方式？ 不能所有图片都只是换个主题的插画。
2. 如何让不同文章、不同图片类型都保持你的个人视觉风格？ 不能每次重新让 AI 决定画风。
3. 如何让生成的图片不仅好看，而且真正帮助读者理解文章？ 尤其是 AI 科普、技术教程、GitHub 项目推荐这些内容。

## 二、现有工作流应该保留什么、改变什么？

根据你提供的代码基线，现有主要流程是：

目前 `image-prompts.json` 主要只有两个控制维度：

- `style_prefix`：整篇文章共享的画风描述。
- `items[].prompt`：每张图片自己的描述。

最终实际请求是把两部分拼接起来。

这个设计对「同一篇文章生成九张统一风格的小王子插画」已经够用，但对于长期维护一个公众号视觉体系，就有些粗糙。

你真正需要的是从：

`全局风格 + 单张提示词`

升级成：

品牌视觉规则 + 图片类型规则 + 文章内容语义 + 单张画面设计 → 最终生图提示词。

这会是本次改造的中心。

## 三、我在代码里发现的 5 个具体改造点

| 问题             | 当前情况                        | 建议                           |
| -------------- | --------------------------- | ---------------------------- |
| 1. 视觉规则没有统一来源  | `style_prefix` 主要靠提示词源头提供   | 建立账号级 Visual Rules           |
| 2. 图片类型不够明确    | 执行器主要区分 cover / body        | 设计层增加 4 种图片类型                |
| 3. 提示词生成与执行分离  | 原有生成脚本没有完整进入当前链路            | 增加统一 Prompt Prepare Workflow |
| 4. 风格变更影响太广    | 修改 `style_prefix` 让全体条目哈希变化 | 将共享规则与类型规则分开                 |
| 5. 图片尺寸和质量检查不足 | 全局尺寸，预览默认首张正文图              | 按用途制定尺寸与检查策略                 |

其中两个问题尤其值得注意。

第一，旧的 `article_image_prompts.js` 已经有不错的设计能力。 它包含内容分析、图位筛选、封面隐喻推导、正文媒介选择及自检。

但它输出的是 `cover.md`、`01.md` 等独立文件，而现在的转换器主要读取 `image-prompts.md` 或 `配图建议.md`。这两部分还需要正式打通，不建议重新写一套完全不同的提示词生成逻辑。

第二，当前转换器存在容易造成旧提示词继续使用的问题。 `convert.mjs` 在发现 `image-prompts.json` 已存在、且未传 `--force` 时，会直接结束。因此，上游 Markdown 改动后，JSON 不一定自动更新。

这应该在此次改造中修复为：检测源内容哈希，未变化直接复用；已变化则重新编译，并对比每张图片的最终提示词。

### 4.1 先建立 `visual-rules.md`

这是从参考资料里应该优先落地的内容。

它不应该只写一句「小王子风格，柔和水彩」，而要把你的视觉习惯拆成真正可执行的参数：

```
brand:
  identity: "个人 AI 技术与知识科普账号"
  palette:
    primary: "待确定"
    background: "待确定"
    accent: "待确定"

  typography:
    chinese: "清晰易读的无衬线字体"
    hierarchy: "主标题 > 核心视觉 > 辅助信息"

  composition:
    whitespace: "充足"
    density: "低到中"
    focal_points: 1

  illustration:
    medium: "柔和水彩或指定系列风格"
    texture: "轻微纸张颗粒"

  fixed:
    - 品牌主色
    - 标题字体体系
    - 核心图形语言

  variable:
    - 主题场景
    - 主体动作
    - 视觉隐喻
    - 局部布局

  avoid:
    - 无意义的霓虹发光
    - 过度饱和
    - 无关装饰元素
    - 拥挤的小字号文字
```

以上是规则结构示例，不代表你的品牌色和长期视觉风格已经确定。

有了它，你写 AI 术语、AI 工作流、GitHub 推荐和 WorkBuddy 教程时，都能沿用同一套账号视觉体系。

同时允许栏目有差异，例如「AI 术语科普」可以偏童话插画，「GitHub 推荐」可以偏技术杂志。它们共享品牌识别，但不必拥有完全相同的构图。

### 4.3 引入 `image-design-plan.json` 中间产物

这部分是为了让 AI 先进行内容设计，再生成最终提示词。

例如一篇关于 Agent 的文章：

```
{
  "article_id": "ai-agent-intro",
  "visual_profile": "ai-knowledge",
  "items": [
    {
      "id": "cover",
      "type": "cover",
      "concept": "AI Agent 从聊天走向执行",
      "layout": "左侧标题，右侧核心主体",
      "aspect_ratio": "2.35:1"
    },
    {
      "id": "term-01",
      "type": "infographic",
      "heading": "## Agent 是怎么工作的",
      "source_facts": [
        "接收任务",
        "制定计划",
        "调用工具",
        "返回结果"
      ],
      "layout": "四阶段横向流程图",
      "aspect_ratio": "16:9"
    }
  ]
}
```

这份 JSON 属于设计计划层，不是直接送给生图 Provider 的文件。

接下来由确定性 Compiler 按固定顺序组合：

```
账号级视觉规则
    +
图片类型专属规则
    +
文章当前图位的内容
    +
构图、边界和输出要求
    ↓
最终 Prompt
```

这样做有两个好处。

首先，AI 不必在每个图位反复自由发挥品牌色、字体、材质等设计决策。

其次，后续你可以只修改一个图位的布局，而不会意外修改其他图的内容和风格。

## 五、最关键的兼容策略：不要直接改掉 D6 契约

这一点我建议明确写入改造方案。

当前 `image-prompts.json` 的 `id`、`heading`、`filename` 都已经被 manifest 和下游插图流程引用。改变这些字段会影响续跑和发布。

2026-10-26-image-gen-flow-and-prompts.md



所以第一阶段仍然输出 V1：

```
{
  "version": 1,
  "article_id": "ai-agent-intro",
  "style_prefix": "账号级共享的画风、色彩与材质要求",
  "items": [
    {
      "id": "term-01",
      "kind": "body",
      "heading": "## Agent 是怎么工作的",
      "prompt": "信息图规则 + 四阶段流程 + 构图要求",
      "filename": "01-agent.png"
    }
  ]
}
```

这里有个很实用的优化：

- `style_prefix` 只存放全部图片真正共享的规则。
- `items[].prompt` 包含该图片类型的专属规则和当前内容。

这样修改信息图模板，只会改变信息图条目的最终 Prompt，避免所有插画和封面跟着失效。

同时增加独立的生成元数据文件，记录 `visual_rules_hash`、图片类型规则版本、源文章哈希和 Compiler 版本，用于检查、追踪和复现。

但要注意：只要最终有效 Prompt 改变，现有哈希机制仍然应该触发失效。不能为了省钱而跳过真正的内容变更检测。

## 六、建议分三个阶段实施

| 阶段         | 工作内容                                                   | 验收结果                |
| ---------- | ------------------------------------------------------ | ------------------- |
| P0：提示词标准化  | Visual Rules、四种类型规则、统一 Prompt Prepare、Compiler、源文件变更检测 | 不付费也能稳定产出结构化提示词     |
| P1：风格和费用优化 | 封面/正文差异化尺寸、风格绑定完善、代表图选择、版本追踪、单图失效                      | 修改一张图不影响无关条目，批量费用可控 |
| P2：成图质量优化  | 图后质量审核、固定 IP 角色、真实截图/数据图渲染、文字合成                        | 提升图文准确性、一致性和可读性     |

P1 还要特别处理一个现有缺口：当前 `IMAGE_GEN_SIZE` 是全局环境变量，但模型指纹主要由 Provider 和模型 ID 构成。建议将实际影响输出的尺寸、质量参数、参考图和规则版本纳入相应的输入指纹，避免设置变化后旧图片仍被当成有效结果。

另外，当前一次 preview 默认只选首张正文图。对于同时有信息图与插画的文章，一张图不足以验证所有视觉类型。初期可以保留单张预览，但要求先审核完整的提示词计划；后续再做按风格类型的代表图确认。

## 七、我建议先做的最小测试

先不要一次性把四种类型的完整图片渲染器全部做完。你可以只选两篇文章作为测试基线：

第一篇：AI 术语科普

验证九张概念插画的视觉统一性、构图变化和角色一致性。

第二篇：GitHub 项目推荐

验证封面、技术架构图和真实项目截图是否能使用不同的视觉形式，同时保留账号识别。

验收时重点检查：

- 同一篇文章的图片是否统一但不重复。
- 不同文章是否有共同的品牌视觉特征。
- 信息图中的概念和文字是否忠实于文章。
- 修改一张正文图的提示词，其他已成功图片是否仍然复用。
- 修改账号级共享规则后，相关风格审批是否正确失效。
- 未获风格确认或预算授权时是否仍能阻止付费批量执行。

最后一项要继续保留你已有的双重审批机制，不能因为引入自动提示词优化而绕开它。

其中 `article_image_prompt_prepare.js` 负责从文章和 Visual Rules 得出设计计划，`compile.mjs` 负责确定性生成原有 D6 格式的 `image-prompts.json`，`convert.mjs` 则继续兼容旧版 Markdown 输入。

我不建议现在就把它扩展成一个通用 AI 设计平台。

你现在最有价值的验证，是使用同一套视觉规则，让公众号文章生成更稳定、减少人工修改提示词的时间、减少失败生图的 API 费用。

这三件事情验证通过后，再增加更复杂的 IP 角色库、视觉资产管理和自动视觉评分，会更有意义。

最终目标不是「让 AI 更会写生图 Prompt」，而是「让你的公众号拥有一套可复用、可审查、可持续改进的视觉设计系统」。 这既服务于现在的文章自动化闭环，也能成为未来面向企业交付内容生产工作流时可以展示的真实案例。
